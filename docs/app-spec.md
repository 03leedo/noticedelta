## 0. 한 줄

**앱은 플랫폼이 돌리는 설정 한 장이다.** 코드를 배포하지 않는다. 어떤 출처에서 무엇을 읽고, 어떤 엔진으로 무엇을 뽑고, 누구에게 무엇이 바뀌면 알릴지를 적는다. 수집, 파싱, 변경 감지, 판정, 알림, 하네스, 운영은 플랫폼이 한다.

## 1. 왜 지금 필요한가

| 이유 | 지금의 문제 |
|---|---|
| 빌더(조종 도구)가 쓸 대상 | 지원사업 앱은 코드 여러 곳에 흩어져 있다. 에이전트가 앱을 만들려면 만들 "물건"이 있어야 한다 |
| 미리 돌려 보기와 비교의 단위 | "이 설정이었다면", "설정을 바꾸면"을 계산하려면 설정이 데이터여야 하고 판(버전)이 있어야 한다 |
| 엔진에 남은 지원사업 지식이 갈 곳 | 속성 사전, 낱말 목록, 변동 값 이름(ARCHITECTURE 9장)이 엔진·공통 안에 있다 |
| 빈 버전 | K-Startup에서 글은 그대로인데 버전만 생긴 것이 200개다. 앱이 읽지 않는 값만 바뀐 경우다. 앱이 무엇을 읽는지 선언해야 거를 수 있다 |

## 2. 무엇이 설정이고 무엇이 코드인가

**원칙: 네트워크를 쓰거나 임의의 계산을 하는 것은 플랫폼 코드, 그 밖은 앱 설정.** 설정은 검증할 수 있고, 판끼리 비교할 수 있고, 과거 기록에 다시 돌려 볼 수 있고, 안전하다.

| 층 | 누가 쓰나 | 모양 | 들어 있는 것 |
|---|---|---|---|
| **출처 카탈로그** | 운영자, 또는 사용자(정해진 커넥터로) | 출처 한 장 (source-catalog.md) | 가져오는 법, 키 목록, 구조화 메타, 무시할 값, 같은 항목 묶기, 이용 조건, 과거 기록 |
| **앱 정의** | 만드는 사람(대개 그 사람의 에이전트) | 설정 한 장 | 읽을 출처와 키, 엔진과 엔진 설정, 구독자 모델, 알림 정책, 민감도, 예산, 표시 이름 |
| **플랫폼 함수 목록** | 플랫폼 개발자 | 코드, 이름으로 고른다 | 값 타입과 비교, 파생 속성 함수(업력, 나이), 묶기 규칙, 맞추기 방식 |
| **엔진** | 플랫폼 개발자(나중에 다른 개발자) | 코드, 엔진 틀(ARCHITECTURE 3.5) | 변경 영향 엔진. 앱은 엔진을 고르고 그 엔진의 설정 칸을 채운다 |

설정으로 안 되는 계산이 필요하면 사용자 엔진(ARCHITECTURE 3.5의 템플릿, 격리 실행)으로 넘어간다.

## 3. 에이전트가 쓰기 좋은 규격

플랫폼을 쓰는 쪽은 대부분 에이전트다. 사람은 말하고, 미리보기를 보고, 중요한 순간에 확인한다.

- **JSON 스키마를 공개한다.** 에이전트는 스키마를 읽고 쓰고, 플랫폼은 저장 전에 검증한다(8장).
- **고칠 방법이 적힌 오류.** "알림의 `fields`에 `amount2`가 없다. 정의된 필드: deadline, amount, …"
- **초안·검증·미리 돌려 보기·비교는 공짜이고 아무것도 남기지 않는다.** 켜기 전에 몇 번이든 돌린다.
- **결과마다 사람에게 보여 줄 문장을 같이 준다.** 에이전트는 그 문장을 그대로 보여 주고 답을 받는다.
- **사람의 확인이 꼭 필요한 순간은 정해져 있다**: 앱 켜기, 판 바꾸기, 사용자 출처 등록(이용 조건 동의), 밖으로 나가는 알림 채널, 예산 올리기. 이 순간은 플랫폼이 사람의 확인 없이 넘어가지 않는다(도구 게이트웨이, ARCHITECTURE 7장).

## 4. 앱 정의 한 장: 지금의 지원사업 앱

저장은 JSON이고, 사람이 읽는 문서에는 같은 내용을 YAML로 적는다.

```yaml
kind: app
id: grant-alerts
version: 3                  # 고칠 때마다 올린다. 켠 판은 바꾸지 않는다
title: 지원사업 정정 알림
owner: user:42              # 6장
sensitivity: personal       # public | personal | sensitive → 하네스 기본값

sources:                    # 카탈로그에서 고른다. 묶기 규칙은 출처에 있다
  - id: bizinfo
    read: [pblancNm, bsnsSumryCn, trgetNm, reqstBeginEndDe, reqstMthPapersCn, refrncNm]
    attachments: true
  - id: kstartup
    read: [biz_pbanc_nm, pbanc_ctnt, aply_trgt_ctnt, aply_excl_trgt_ctnt, biz_enyy,
           biz_trgt_age, supt_regin, prfn_matr, aply_trgt, supt_biz_clsfc, prch_cnpl_no,
           pbanc_rcpt_bgng_dt, pbanc_rcpt_end_dt]

engine:
  kind: change_impact@1     # 엔진을 바꾸면 이 칸을 바꾼다. 아래 칸은 이 엔진의 설정이다
  fields:
    deadline:
      type: datetime
      from: {meta: apply_end}         # 출처가 구조화해 준 값. LLM을 부르지 않는다
      else: extract                   # 메타가 없으면 글에서 뽑는다
      guide: 신청 마감 일시
      keywords: [마감, 접수 기간, 신청 기간, 모집 기간, 소진 시까지]
    amount:
      type: amount
      from: extract
      guide: 기업당 최대 지원 금액(원)
      keywords: [지원금, 지원 규모, 지원 한도, 사업비, "최대 \\d"]
    eligibility_rules:
      type: ruleset                   # subjects.attributes 위의 규칙식
      from: extract
      guide: 신청 자격
      keywords: [신청 자격, 지원 대상, 자격 요건, 제외 대상, 업력, 연령, 소재, 예비 창업, 매출]
    required_documents: {type: list, from: extract, guide: 제출 서류 이름, keywords: [제출 서류, 구비 서류, 증빙]}
    contact: {type: text, from: extract, guide: 문의처, keywords: [문의, 연락처, 담당자]}

subjects:
  model: rules                      # rules | watchlist | everyone
  rules_field: eligibility_rules
  attributes:                       # 이름과 타입만. 값은 개인정보 금고에 있다
    founded_on:          {type: date, label: 창업일}
    ceo_birth_date:      {type: date, label: 대표자 생년월일}
    business_age_months: {type: int, derive: months_since(founded_on), label: 업력(개월)}
    ceo_age:             {type: int, derive: age(ceo_birth_date), label: 대표자 나이}
    region_sido:         {type: enum, values: [서울, 부산, 대구, …, 제주], label: 사업장 소재지}
    business_type:       {type: enum, values: [individual, corporation], label: 사업자 형태}
    revenue_krw:         {type: int, label: 작년 매출(원)}
    employees:           {type: int, label: 상시 근로자 수}
    is_pre_founder:      {type: bool, label: 예비 창업}
    is_women_owned:      {type: bool, label: 여성기업}
    is_restart:          {type: bool, label: 재창업}

alerts:
  rules:
    - on: verdict_changed           # 판정이 바뀐 사람에게
      urgent: [eligible→ineligible] # 나머지는 묶어서
    - on: field_changed
      fields: [deadline, amount, required_documents]
      to: subscribers
  channels: [inbox, email]          # 구독자 본인에게 가는 채널만 기본(7장)
  hold:
    mass_impact: 20                 # 한 변경이 이만큼 넘는 사람을 비해당으로 바꾸면 붙잡는다
    min_confidence: 0.7             # 인용 검증을 통과하지 못한 값은 "확인 필요"

budget: {llm_usd_per_month: 5, on_exceed: pause_extraction}   # 9장

labels:
  fields: {deadline: 마감일, amount: 지원 금액, eligibility_rules: 신청 자격,
           required_documents: 제출 서류, contact: 문의처}
  results: {eligible: 해당, ineligible: 비해당, unknown: 확인 필요}
```

## 5. 두 번째 예시로 틀 검증: 약국 앱 (가상)

규격이 지원사업에만 맞는지 보려고 모양이 다른 앱을 하나 더 적어 본다. **출처와 키 이름은 가정이다**(카탈로그에 아직 없다).

```yaml
kind: app
id: pharmacy-permits
version: 1
title: 우리 약국 약 허가 사항 변경 알림
owner: user:77
sensitivity: public

sources:
  - id: mfds_permits                # (가상) 의약품 허가 사항 변경 공개 목록. 품목 번호로 묶는다
    read: [item_name, ingredient, change_type, change_text, changed_on]
    attachments: false

engine:
  kind: change_impact@1
  fields:
    item_name:  {type: text, from: {meta: item_name}}
    ingredient: {type: text, from: {meta: ingredient}}
    dosage:     {type: text, from: extract, guide: 용법·용량, keywords: [용법, 용량, 1회, 1일]}
    warnings:   {type: list, from: extract, guide: 사용상 주의사항 항목, keywords: [주의, 금기, 투여하지]}

subjects:
  model: watchlist                  # 구독자가 낸 목록과 항목 필드가 겹치면 해당
  match: {field: ingredient, normalize: korean_drug_name}
  list_label: 우리 약국 재고 성분

alerts:
  rules:
    - on: field_changed
      fields: [dosage, warnings]
      to: matched
      urgent: [warnings]
  channels: [inbox]
  hold: {mass_impact: 200, min_confidence: 0.7}

budget: {llm_usd_per_month: 2, on_exceed: pause_extraction}
labels:
  fields: {dosage: 용법·용량, warnings: 주의사항}
```

**틀이 버틴 것**: 출처·엔진·구독자·알림·하네스·예산이 같은 자리에 들어간다. 구독자 모델만 바꾸면 된다(`rules` → `watchlist`). 필드의 `from: meta`로 LLM 없이 도는 앱도 된다.

**틀이 드러낸 빈 곳** (12장): 성분 이름 맞추기 같은 도메인 지식을 설정으로 적기 어렵다. 출처가 "변경 내역"을 직접 주는 경우에는 조각 비교가 필요 없을 수 있다(다른 엔진이 필요하다는 뜻일 수 있다).

## 6. 사람과 권한

| 역할 | 할 수 있는 것 |
|---|---|
| **소유자** (앱을 만든 사람) | 앱 정의를 고치고, 미리 돌려 보고, 켜고 끄고, 예산을 정한다. 사용자 출처를 등록한다 |
| **구독자** (앱을 쓰는 사람) | 링크나 초대로 들어와 자기 정보(속성 값, 목록)를 넣고 알림을 받는다. 다른 구독자는 보지 못한다 |
| **관리자** (기관) | 구독자 여럿의 정보를 대신 관리한다(창업지원단이 보육기업 여러 곳을 맡는 경우). 구독자의 동의가 필요하다 |

- 한 사람이 여러 앱을 구독할 수 있다. 같은 속성(예: 창업일)은 금고에 한 번 두고, 앱마다 용도별 동의를 받는다.
- 지금의 "링크 하나 = 프로필 하나"는 구독자 한 명, 앱 하나인 경우다. 링크는 그대로 쓰고 그 위에 소유자·관리자를 얹는다.
- 2026-11-26: 소유자를 `app_member`에 둔다. 에이전트가 조종 도구(`save_app` 등)로 새 앱을 저장하면 그 세션의 사람이 소유자가 되고, 있는 앱은 소유자만 고치고 켠다. 켜기는 늘 소유자의 확인을 받는다(platform-services 5.14). 관리자(기관이 여러 구독자를 맡기)는 아직 없다.
- 2026-11-27: **관리자**(`managers.py`, 표 `manage_invite`·`manage_link`, 마이그레이션 0020). 관리자가 초대 링크를 만들고(구독자에게 보일 이름을 적는다, 7일 동안 여러 사람이 받는다) 구독자가 내 링크로 받아들이면 연결된다. 동의는 금고의 `manage` 용도로 그 사람이 넣어 둔 키에 남는다. 관리자는 연결이 살아 있을 때만, 동의한 키만 보고 고친다(볼 때마다 접근 기록). 구독자는 "내 관리자"에서 끊고, 그 앱의 다른 관리자가 없으면 동의도 철회된다. 내 정보를 지우면 연결도 모두 닫힌다. 웹: `/p/<토큰>/manage`(내가 맡은 사람과 자격 요약), `/invite/<코드>`, `/p/<토큰>/managers`.

## 7. 알림

- **채널과 능력 속성**: 화면 알림함, 이메일, 캘린더처럼 구독자 본인에게 가는 채널은 기본으로 쓸 수 있다. 웹훅처럼 밖의 주소로 보내는 채널은 외부 효과(C)라서 도구 게이트웨이의 승인 뒤에만 쓸 수 있다.
- **판을 바꿀 때의 알림 폭탄 막기**: 새 판을 켜면 규칙이나 필드가 바뀌어 판정이 대량으로 달라질 수 있다. 이것은 공고의 정정이 아니므로 정정 알림으로 보내지 않는다. 구독자에게는 한 번만 요약해 알리거나(예: "자격 기준이 바뀌어 3개 사업의 결과가 달라졌습니다") 조용히 반영한다. 어느 쪽인지는 켤 때 소유자가 고른다.

## 8. 검증 규칙 (앱을 저장하기 전에)

- 출처는 카탈로그에 있고 소유자가 쓸 수 있어야 한다(사용자 출처는 소유자만). `read`의 키는 그 출처가 내는 키여야 한다.
- 엔진은 플랫폼에 등록된 엔진이어야 하고, 엔진 칸은 그 엔진의 스키마를 따른다.
- 필드(변경 영향 엔진): 이름이 겹치지 않는다. `type`은 정해진 것(datetime, amount, ruleset, list, text, enum)만. `from: meta`면 카탈로그가 내는 메타 키여야 하고, `extract`면 `guide`가 있어야 한다.
- 구독자: `rules`면 `rules_field`가 ruleset 필드여야 하고 `attributes`가 있어야 한다. `derive`와 `normalize`는 플랫폼 함수 목록에 있는 이름만.
- 알림: `fields`는 정의된 필드여야 한다. 밖으로 나가는 채널은 승인 기록이 있어야 한다. `hold`는 범위 안의 값만.
- 민감도: `personal` 이상이면 개인정보 가리기를 끌 수 없다. `sensitive`는 외부 모델로 보내지 않는다(로컬 모델이 생기기 전까지는 켤 수 없다).
- 예산: 있어야 한다. 한도: 필드 수, 낱말 수, 구독자 목록 크기, 출처 수.

## 9. 판·공유·비용

- **판**: `version`과 내용 해시를 함께 쓴다. 켠 판은 바꾸지 않는다. 플랫폼이 만드는 결과(필드 값, 판정, 알림)에는 어느 앱의 어느 판으로 계산했는지 남긴다. 새 판을 켜면 지금 상태를 새 판으로 다시 계산하고(비용을 먼저 보여 준다, 7장의 알림 처리), 과거는 다시 쓰지 않는다.
- **수집·원문은 출처 단위로 한 번.** 여러 앱이 같은 출처를 읽어도 한 번 받고 한 번 파싱한다(RQ10).
- **변경은 앱이 읽는 것 기준.** 출처 단위의 버전 하나를 두고(앱들이 읽는 키의 합집합), 본문 조각마다 어느 키에서 왔는지 적는다(`locator.key`). 앱은 자기가 읽는 키의 조각이 바뀐 변경만 받는다. 빈 버전 200개는 이것으로 풀린다.
- **필드 추출은 앱 단위.** 같은 정의(필드 이름·타입·안내가 같음)는 녹화본 키가 같아 한 번만 부른다.
- **비용과 한도**: 앱마다 LLM 예산을 둔다. 넘으면 추출을 멈추고(수집과 메타 필드는 계속), 소유자에게 알린다. 미리 돌려 보기와 새 판 켜기 전에 예상 비용을 보여 준다(평가 틀의 입력 크기 계산을 쓴다). 무료 한도와 누가 내는지는 운영 방식이 정해질 때 정한다. 2026-11-25: 게이트웨이에 미리 세기(`Mode.PLAN`: 녹화본에 없는 호출만 골라 크기를 센다)와 토큰 예산(`Budget`: 넘을 호출은 보내기 전에 막고, 실패한 호출이 쓴 토큰도 센다)을 넣었다. 지금은 실행 단위다. 앱 단위·하루 단위 누적은 사용 기록과 함께 붙인다.

2026-11-25: 운영 워커에 추출기를 붙였다(`scripts/worker.py --extract`).
- **출처 값 필드**: 앱 정의의 `from: meta` 필드(마감)는 LLM에 묻지 않고 출처 값(`programs.source_meta`, 카탈로그 이름)으로 읽어 앞 판과 비교한다. 제목에 [마감]이 붙으면 "마감"이다.
- **범위**(`--scope`): `subscribed`(구독자가 있는 사업, 기본), `changed`(정정이 생긴 사업), `all`. 범위에 들어온 사업은 첫 판부터 차례로 계산한다(`enqueue_item_impact`). 워커는 추출을 켤 때마다 구독 사업 가운데 아직 계산하지 않은 것을 넣는다(`enqueue_scope_backlog`).
- **따라잡기는 알리지 않는다**: 범위에 늦게 들어온 사업의 지난 판은 값·판정만 채우고 알림을 내지 않는다. 지난 정정을 지금 구독자에게 새로 알리지 않게. 알림은 그 뒤에 새로 온 정정부터다.
- **읽는 키 밖의 출처 값 변경**: 앱이 읽지 않는 키만 바뀐 판이어도 출처 값 필드(마감)가 바뀌었으면 그 필드만 비교한다(LLM 없음). 출처 값(날짜만)과 LLM 값(시각 포함)은 한쪽에 시각이 없으면 날짜만 비교한다.
- **하루 한도**(`--daily-tokens`, 기본 `NOTICEDELTA_LLM_DAILY_TOKENS` 또는 20만, 한국 시간 자정 기준): 워커가 영향 계산 작업마다 보낸 토큰(실패한 호출 포함)을 작업 트랜잭션과 따로 바로 커밋한다(`record(kind=llm_usage)`). 그 합으로 오늘 쓴 양을 세고 남은 만큼만 보낸다. 한도에 닿으면 더 꺼내지 않고, 걸린 작업은 시도 횟수를 쓰지 않고 미룬다(`jobs.Deferred`).
- **녹화본**: 같은 요청은 녹화본에서 꺼내고, 새로 보낸 호출도 녹화한다(재생·미리 돌려 보기에 쓴다).
- **첫 실측**(최근 정정된 사업 2개, 판 4개): LLM 호출 3개, 토큰 3,090. 한 사업은 마감 변경(2026-12-31 → 2027-12-31)을 출처 값으로 잡았고(LLM 없음), 다른 사업은 자격 규칙 변경을 LLM으로 잡았다. 운영 DB에 사람·구독이 아직 없어 알림은 없다.

2026-11-26: **여러 앱이 함께 돈다**(플랫폼 8번의 완료 기준).
- 수집·파싱·변경 기록은 출처 단위로 한 번이다. 변경이 기록되면 켠 앱마다 영향 계산 작업을 따로 넣는다. 그 항목의 출처를 읽지 않는 앱은 넣지 않는다.

## 10. 미리 돌려 보기와 비교

### 10.1 미리 돌려 보기 (backtest)

```text
입력  앱 정의(초안이어도 됨) · 기간(예: 지난 90일) · 구독자(만든 사람의 정보, 또는 가상 구독자 N명)
돌림  기록된 수집 실행을 시간 순으로 다시 흘린다. 다시 수집하지 않는다.
      앱이 읽는 키로 판을 만들고 → 필드를 뽑고(녹화본, 없으면 비용을 보여 주고 묻는다) → 판정·알림을 계산한다.
      알림은 보내지 않고 목록으로만 낸다.
출력  알림 목록(언제·누구에게·무엇이 어떻게·근거 조각) · 요약(건수, 확인 필요 비율, 붙잡힘, LLM 호출·비용)
      · 기록의 빈틈(이 기간 수집하지 못한 구간 n곳, 그 사이의 중간 판은 놓쳤을 수 있다)
```

- LLM 키가 없으면 `from: meta` 필드만 계산된다. 나머지 필드는 "녹화본 없음"으로 표시한다(평가 틀과 같다).
- 사람은 알림 카드마다 맞다/틀리다를 누른다. 이것이 **앱의 시험**이 된다.

### 10.2 비교 (compare)

```text
입력  두 판(켠 판과 초안, 또는 두 초안) · 같은 기간 · 같은 구독자
출력  생긴 알림 · 사라진 알림 · 내용이 바뀐 알림, 그리고 깨진 시험(맞다고 표시한 알림이 사라지거나 바뀜)
```

- "용량 변경은 빼 줘" → 초안을 만들고 비교 → "알림 3건이 사라집니다. 그중 1건은 전에 맞다고 표시하셨습니다."
- 평가 틀(`evaluation`)의 방식 비교와 같은 엔진을 쓴다. 방식 대신 앱 판을 바꿔 끼운다.

**검증 화면 (2026-11-27)**: 웹 `/p/<토큰>/apps`에서 소유자가 내 앱의 상태(11장)를 보고, `/p/<토큰>/apps/<앱>`에서 판 두 개(기본은 켠 판 대 가장 새 판)를 골라 고친 자리(정의의 경로별 앞·뒤 값)와 기록된 정정으로 다시 돌린 결과(알림 수, 새로 생긴·사라진·바뀐 알림, 깨진 시험)를 나란히 본다. 녹화본만 쓰므로 비용이 들지 않는다.

### 10.3 앱의 시험과 평가 라벨은 같은 모양

사람이 단 "맞다/틀리다"와 연구용 사람 라벨(5a, `label` 테이블)을 같은 모양으로 둔다: (항목 버전, 필드 또는 알림, 판단, 누가, 언제). 사용자가 쓸수록 평가 데이터가 쌓이고, 연구 측정(RQ1)과 앱 시험이 같은 데이터를 본다. 구독자의 판단을 연구에 쓰는 것은 선택 동의를 한 경우만이다.

2026-11-24: 규격을 코드로 옮겼다(`appspec.py`, 공개 스키마 `docs/app-schema.json`). 지원사업 앱은 정의 한 장(`src/noticedelta/apps/grant-alerts.json`)이 되었고, `grants`·`names`는 그 정의를 읽어 예전 이름으로 내놓는다. 옮기면서 엔진이 보는 값(LLM 안내, 낱말, 속성 사전과 순서, 붙잡기 기준)이 한 글자도 바뀌지 않았음을 시험으로 고정했다(녹화본 키가 그대로다). 같은 날 이어서: 정의의 원본을 DB(`app_definition`, `app_registry.py`)로 두고 파이프라인이 시작할 때 저장소의 정의를 씨앗으로 넣는다. 같은 판 번호에 다른 내용이 오면 막는다("version을 2로 올린다"). 넣기(register)와 켜기(enable)를 나눠, 켜기는 사람의 확인 자리로 남겼다(씨앗은 운영자가 저장소에서 확인한 것이라 바로 켠다). 필드 값·판정·구독·라벨·알림에 `app_id`·`app_version`을 달고(마이그레이션 0010, 지난 결과는 판 1로 채움), 파이프라인과 화면은 자기 앱의 결과만 읽는다. 알림의 멱등 키 앞에 앱 ID를 붙여 두 앱이 같은 필드 이름을 써도 서로 막지 않는다. 남은 것: 출처 한 장, 이름을 항목으로. (둘 다 같은 날 끝냈다: source-catalog.md 7장, 마이그레이션 0011. 플랫폼 층에 `program` 낱말이 있으면 `tests/test_layers.py`가 깨진다.)

- 판정의 유일 조건(사람·사업 판·규칙 해시)은 그대로 두었다. 규칙이 같으면 앱이 달라도 판정이 같기 때문이다. `app_id`는 먼저 계산한 앱이 남는다.
- 결과 테이블에서 `app_definition`으로 외래 키는 걸지 않았다(시험·도구가 결과만 만들 때가 있다). 파이프라인은 결과를 쓰기 전에 정의를 넣는다.

- 정의 파일은 주석을 못 달아서 필드에 `note`(사람이 읽는 메모, 엔진은 쓰지 않음)를 두었다.
- 규격의 타입 이름 `ruleset`은 엔진의 값 타입 `rules`로 바꿔 넘긴다.
- 출처의 `read` 키와 `from: {meta: …}`는 출처 카탈로그(source-catalog.md 7장)에 있는 것만 쓸 수 있다(`check_app(sources=, meta=)`, 2026-11-24).

2026-11-25: 변경을 앱이 읽는 것 기준으로 거른다(13장의 3번, 판 단위). 변경을 기록할 때 원본 항목에서 바뀐 키를 출처 한 장의 기준으로 계산해 이벤트에 남기고(`SourceSheet.changed_keys`: 무시하는 키·주소 키는 빼고 표기 차이는 같게, 항목 판을 가르는 기준과 같다), 앱은 바뀐 키가 자기가 읽는 키와 겹치거나 자기가 읽는 첨부가 바뀐 판만 변경으로 받는다(`AppDefinition.reads_change`). 아니면 영향 계산이 LLM을 부르지 않고 앞 판의 값을 상태까지 그대로 넘긴다. 판을 건너뛰지 않고 값을 넘기는 이유는 영향 계산이 판마다 이어지는 사슬이라서다(다음 판은 앞 판의 결과를 읽는다). `change.detected` 봉투에도 바뀐 키가 실린다.

- 실제 DB(첫 판을 뺀 변경 60건, `scripts/change_keys.py`): 앱이 읽지 않는 키만 바뀐 판 4건(기업마당 `hashtags` 3, `printFileNm` 1), 조각이 하나도 안 바뀐 판 5건(제목만, 표기만). 9건 모두 영향 계산에서 LLM을 부르지 않는다. 앞서 문제였던 K-Startup 빈 버전 200개는 형식 변화 감시(source-catalog 5장)가 먼저 붙잡아 지금 DB에는 없다. 새 키(`eval_method`, `support_ctnt`)를 받아들여도 이 앱은 읽지 않으므로 변경이 아니다.
- 남은 것: 본문 조각마다 원본 키를 적기(`locator.keys`). 지금은 앱이 하나이고 본문이 그 앱이 읽는 키로만 만들어져 판 단위로 충분하다. 두 앱이 같은 출처의 다른 키를 읽게 되면, 엔진이 자기 키의 조각만 보도록 조각 단위로 내려가야 한다.

2026-11-25: 추출을 앱 정의로 만든다(`extraction.py`, 엔진 층). 이전까지 추출기는 지원사업 팩의 전역값(필드 타입·안내, 시스템 프롬프트, 자격 속성 사전)에 묶여 있어 두 번째 앱이 추출할 길이 없었다.

- 추출에 필요한 것을 `ExtractSpec` 하나에 담는다: 필드 타입·안내, 규칙 속성 사전, 틀별 시스템 프롬프트, 조각 머리말.
- `spec_for_app(app)`은 앱 정의만으로 일반 프롬프트를 만든다. 분야·머리말·참고 줄은 선택 칸 `engine.prompt`에서 읽고, 없으면 앱 제목을 분야로 쓴다. 규칙 필드가 없는 앱은 자격 규칙 안내를 넣지 않는다. 출처 값으로만 읽는 필드는 LLM에 묻지 않는다.
- 지원사업 팩(`llm.extract`)은 자기 프롬프트를 글자 그대로 준다. 일반 생성기가 같은 글자를 내는지는 불러올 때와 시험으로 확인한다. 평가 표가 리팩터링 전과 한 글자도 같았다(녹화본 그대로, 토큰 0).
- 파이프라인은 지원사업 전역값 대신 켠 앱(`ctx.app`)에서 필드 목록, 낱말 탐지기, 규칙 필드, 붙잡기 기준을 읽는다. 지원사업 팩에서 가져오는 것은 운영하는 앱의 기본값(`APP`) 하나다.
- 미리 돌려 보기는 앱마다 추출기를 만든다. 필드 안내를 바꾼 초안은 요청이 달라져 녹화본이 없다. `--plan`으로 비용을 센다. 금액 안내 한 줄을 고친 초안은 개발 세트를 다시 돌리는 데 호출 59개, 입력 토큰 약 62만이 든다. 안내는 모든 추출 요청에 들어가므로, 한 줄을 고쳐도 녹화본이 모두 무효가 된다.
- 시험: 약국 앱(5장)이 지원사업 코드 없이 자기 정의로 요청을 만든다(`tests/test_extraction.py`).
- 출처가 다른 게시물로 이어진 판(다른 출처로 옮겨 간 항목), 예전 기록처럼 무엇이 바뀌었는지 모르면 받는다. 놓치는 것보다 낫다.

| 3 | 본문 조각에 원본 키 적기, 앱이 읽는 키 기준으로 변경 거르기 | K-Startup 빈 버전 200개가 변경 목록에서 사라진다 |
| 4 | 미리 돌려 보기(빈틈 표시 포함) | 지원사업 앱으로 지난 기간의 알림 목록이 나온다(LLM 없이는 마감일만) |
| 5 | 비교와 앱의 시험, 플랫폼 회귀 시험 | 판 두 개의 알림 차이와 깨진 시험이 나온다. 플랫폼을 고칠 때마다 모든 앱의 결과 차이가 나온다(15장) |
| 6 | MCP 조종 도구: `list_sources`, `draft_app`, `validate_app`, `backtest`, `compare_app`, `enable_app` | 에이전트가 말로 받은 요구를 앱 정의로 만들고, 미리 돌려 보고, 사람의 확인을 받아 켠다 |
| 7 | 사용자 출처 등록(`rss`, `html_list`, `file_drop`) | 에이전트가 주소 하나로 출처를 등록하고 사람의 확인을 받는다 |
| 8 | 소유자·구독자·관리자, 예산, 판 바꾸기의 알림 처리, 상태 보고 | 다른 사람이 만든 앱이 내 앱과 섞이지 않고 돈다 |
| 9 | 두 번째 앱을 실제 출처로 올리고 규격을 확정한다 | 두 번째 앱이 플랫폼 코드를 거의 고치지 않고 돈다(RQ7) |
