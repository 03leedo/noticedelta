> 비전공자도 말로 앱을 만들면 플랫폼이 배포·운영·검증·보안을 맡는 방향까지 담은 큰 틀 문서.

## 0. 한 줄 요약

**만들고 싶은 것을 말하면 에이전트가 엔진과 앱을 조립하고, 배포·운영·보안·검증은 플랫폼이 맡아서, 만든 사람은 "의도대로 도는지"만 확인하면 되는 플랫폼.** 첫 엔진은 "문서나 데이터가 바뀌면 영향받는 사람만 찾아 알리는" 변경 영향 엔진이고, 엔진은 같은 틀(3.5)에 맞춰 갈아 끼운다.

- AI 모델을 만드는 것이 아니다. Claude 같은 모델은 API로 호출하는 부품이다.
- 쓰는 사람은 셋이다.
  - **앱 사용자**: 플랫폼을 보지 않는다. 설치 없이 링크·캘린더·알림으로 앱만 쓴다.
  - **앱 만드는 사람(비전공자 포함)**: 빌더 에이전트에게 말로 설명하고, 백테스트·비교 화면으로 확인한 뒤 켠다. 서버를 몰라도 된다(3.6).
  - **엔진 만드는 사람(개발자)**: 엔진 틀을 지켜 새 엔진을 올리거나 기존 엔진을 바꿔 끼운다. SDK·이벤트·MCP를 쓴다.
- 차별점은 "말하면 만들어 준다"가 아니라(이미 여러 서비스가 한다), **바꾸면 무엇이 달라지는지 보여 주는 검증**과 **민감한 데이터도 쓸 수 있는 기본 보안**이다.

## 1. 왜 플랫폼인가

1. **앱 하나로는 엔진이 보이지 않는다.** 밖에서 보면 지원사업 알림 앱은 "공고를 받아 LLM으로 요약해 알린다"와 구분되지 않는다. 같은 엔진이 다른 도메인에서도 돌아야 "특정 앱의 로직이 아니라 엔진"이라는 주장이 선다.
2. **서비스마다 같은 기능이 반복된다.** 수집 주기, 문서 파싱, 알림 발송, 개인정보 보관, LLM 호출 관리는 어느 서비스든 다시 만든다. 한 번 잘 만들어 함께 쓴다.
3. **에이전트를 붙이면 보안 문제가 구조적으로 생긴다.** 공고를 읽고(신뢰할 수 없는 입력), 내 서류를 보고(민감 데이터), 기관에 메일을 보내는(외부 효과) 에이전트는 세 능력을 모두 갖는다. 서비스마다 막지 말고 플랫폼 한 곳에서 통제한다(이전 보고서의 도구 게이트웨이).
4. **비전공자는 배포·운영을 못 한다.** 서버 세팅, 트래픽, 백업, 장애 대응을 모른다. 앱을 서버가 아니라 **설정**으로 만들면 이 일이 플랫폼 하나의 일이 된다(3.4, 3.6).
5. **비전공자는 코드를 못 읽으니 결과로만 확인할 수 있다.** "고쳐 달라고 했더니 다른 게 망가진" 일을 막으려면, 바꾸기 전과 후를 실제 기록으로 다시 돌려 **달라진 결과만** 보여 줘야 한다. 이것은 변경 영향 엔진이 공고 정정에 하는 일과 같은 일이다.

## 2. 전체 구조

```text
┌─ 빌더 ───────────────────────────────────────────────────────────┐
│  말 → 빌더 에이전트 → 템플릿 선택 → 엔진 코드·앱 설정 → 검증 → 켜기     │  3.6
└──────────────────────────────┬───────────────────────────────────┘
┌─ 앱 ─────────────────────────▼───────────────────────────────────┐
│  신청 준비함 (1단계)     출발 알리미 (후보)     의존성 영향 분석 (후보) │
│  지원사업 팩             교통 공지 팩            보안 권고 팩           │
│  + 신청 에이전트                                 + 수정 PR 에이전트     │
└──────┬───────────────────────┬──────────────────────┬─────────────┘
       │        도메인 팩 규약 (출처 · 필드 · 구독자 모델 · 싱크)  4장
┌──────▼───────────────────────▼──────────────────────▼─────────────┐
│ 엔진 틀       이벤트 → 결정. 능력 선언, 부수 효과는 게이트웨이로      3.5 │
│ 플랫폼 엔진   변경 영향 엔진 (지금의 NoticeDelta 엔진) · 스트림 엔진(후보) │
│              · 템플릿으로 만든 사용자 엔진                               │
├────────────────────────────────────────────────────────────────────┤
│ 플랫폼 공통   알림 발송 · 문서 파싱 · 수집 스케줄러 · 개인정보 금고       │
│              도구 게이트웨이 · LLM 게이트웨이(+하네스) · 비행 기록기       │
│              검증(백테스트·비교·하네스 실험) · 작업 큐 · MCP             │
├────────────────────────────────────────────────────────────────────┤
│ 표준 부품     인증 · 검색 · 관측 · 비밀값        (가져다 쓴다)           │
├────────────────────────────────────────────────────────────────────┤
│ 인프라        여러 앱이 함께 도는 런타임 · KEDA · Terraform · PostgreSQL   │
└────────────────────────────────────────────────────────────────────┘
```

- (2단계 이후 목표) 층 사이는 **이벤트(5.1)와 MCP 도구(5.2)로만** 연결한다. 1단계는 모듈형 모놀리스이고, 웹은 읽기 전용 뷰로 DB를 직접 읽으며 엔진 테이블에는 쓰지 않는다.
- 에이전트의 외부 효과는 모두 도구 게이트웨이를 거친다(7장).

## 3. 층별 책임

### 3.1 플랫폼 엔진

**변경 영향 엔진**: 버전이 붙은 문서를 받아 "무엇이 바뀌었고, 어느 필드가 영향을 받았고, 누구의 결과가 실제로 달라졌는지"를 계산해 이벤트로 낸다. 지금 저장소의 모듈 대부분이 여기에 속한다.

| 엔진 단계 | 지금 모듈 | 범용화할 때 바뀌는 점 |
|---|---|---|
| 조각화 | `segments.py` | 문서 파싱 서비스(3.2)의 출력 형식을 그대로 받는다 |
| 조각 맞추기 | `matching.py` | 바뀌지 않음 |
| 타입별 비교 | `values.py` | 타입을 팩이 등록할 수 있게 한다 (날짜·금액·집합은 기본 제공) |
| 인용 검증 | `citation.py` | 바뀌지 않음 |
| 영향 계산 | `impact.py` | 필드 정의와 구독자 모델을 팩에서 받는다 |
| 대상 계산 | `eligibility/` | 조건식 → SQL은 기본 구독자 모델이 된다. 속성 사전은 팩으로 옮긴다 |
| 신뢰성 | `db/` | 버전 순서 보장, 작업 원장은 엔진에, 아웃박스는 알림 발송(3.2)으로 |

엔진이 지키는 성질:
- **LLM 호출 수가 구독자 수와 무관하다.** 구독자 쪽 계산은 코드(SQL)로만 한다.
- **의미 기반 멈춤.** 다시 추출한 값이 타입별 비교로 같으면 아래로 전파하지 않는다.
- **근거 체인.** 조각 → 필드 → 규칙 → 판정 → 알림을 모두 이어서 저장한다. `explain`(5.2)과 레이블 전파(7장)가 이것을 쓴다.
- **버전은 뒤로 가지 않는다.** 늦게 온 옛 버전이 새 결과를 덮지 않는다.

**스트림 엔진 (후보, 출발 알리미 단계)**: 초 단위로 들어오는 위치 이벤트를 받아 상태(도착 예측)를 갱신하고, 영향받는 구독자만 다시 계산한다. 변경 영향 엔진과 같은 이벤트 형식(5.1)을 쓴다. 필요해질 때 만든다.

### 3.2 플랫폼 공통 (직접 만든다)

어느 서비스든 쓰면서, 이 플랫폼에서 만들 이유가 있는 것만 직접 만든다.

| 서비스 | 책임 | 지금 있는 것 |
|---|---|---|
| **알림 발송** | 채널(이메일·웹 푸시·웹훅), 사용자별 수신 설정, 방해 금지 시간, 급한 것만 바로·나머지는 묶음 발송, 정확히 한 번(멱등 키), ICS 캘린더 구독, 보류 상태(7장) | 아웃박스와 멱등 키 (`db/`) |
| **문서 파싱** | HWP/HWPX/PDF/HTML → 위치(`locator`)가 붙은 조각 JSON. 네트워크 차단·읽기 전용·자원 제한 컨테이너. 실패하면 `needs_review` | 조각화 (`segments.py`) |
| **수집 스케줄러** | 출처별 주기 결정(변경 빈도 추정·마감 임박도·구독자 수), 속도 제한, 서킷 브레이커, 재시도. 바뀐 것만 다음 단계로 | 속도 제한·서킷 브레이커 (`sources/resilience.py`) |
| **개인정보 금고** | 프로필·업로드 서류·위치 같은 민감 데이터 보관, 용도별 동의 기록, 보관 기한, **용도와 세션 상태로 범위를 줄인 토큰**으로만 꺼냄 | 없음 |
| **도구 게이트웨이** | 에이전트 도구 호출의 능력 선언, 세션 상태 추적, 전이 시점 정책, 보류 후 확정 (7장) | 없음 (이전 보고서 5장 제안) |
| **LLM 게이트웨이** | 모델 라우팅, 녹화·재생, 캐시, 토큰·비용 집계, 앱별 예산, **하네스**(아래) | 녹화·재생·비용 집계 (`llm/gateway.py`) |
| **검증** | 틀을 지킨 엔진·앱이면 무엇이든: 백테스트(과거 기록으로 미리 돌려 보기), 버전·엔진 비교(달라진 결과만), 하네스 실험(하네스를 바꿔 다시 돌린 지표 비교) | 재생 (`history.replay`), 라벨 평가 (`labeling/`), 지표 (`metrics.py`) |
| **비행 기록기** | 에이전트 실행(프롬프트·도구 호출·결과)과 엔진 이벤트를 이벤트 소싱으로 저장, 결정적 재생, 프롬프트를 바꿔 재생한 결과 비교 | LLM 녹화본 (`llm/cassette.py`) |
| **작업 큐** | 단계별 워커, 재시도 3회 후 실패 큐, 미확인 작업 회수, KEDA 자동 확장 지표 | 작업 원장 (`db/`) |
| **MCP 서버** | 엔진·앱 기능을 외부 에이전트에 도구로 제공 (5.2). 반드시 도구 게이트웨이 뒤에 둔다 | 없음 |

**하네스**: LLM 호출 앞뒤에 끼우는 단계들. 앱 설정의 민감도 등급에 따라 플랫폼이 기본으로 켠다. 목록은 초안이다.

| 위치 | 하네스 | 하는 일 |
|---|---|---|
| 입력 | 개인정보 가리기 | 주민번호·전화·이름 등을 가린 채 보내고 응답에서 되돌린다 |
| 입력 | 인젝션 탐지 | 공고·첨부·사용자 입력에 숨은 지시를 찾아 표시하거나 막는다 |
| 라우팅 | 민감도별 모델 | 민감 등급이면 외부 API 대신 로컬·학내 모델로 보낸다 |
| 출력 | 근거 인용 검사 | 말한 값이 원문 조각에 실제로 있는지 본다 (`citation.py`) |
| 기록 | 감사 기록 | 누가 어떤 데이터를 어느 모델에 보냈는지 비행 기록기에 남긴다 |

### 3.3 표준 부품 (가져다 쓴다)

직접 만들어도 차별점이 생기지 않는 것은 검증된 오픈소스를 붙인다.

| 기능 | 후보 | 이유 |
|---|---|---|
| 인증·계정 | Keycloak 또는 Ory | 소셜 로그인·세션·토큰 발급은 직접 만들 이유가 없다 |
| 검색 | PostgreSQL 전문 검색 + pgvector | DB를 하나 더 두지 않는다 |
| 관측 | OpenTelemetry, Prometheus, Grafana | DESIGN.md 9.4와 같다 |
| 비밀값 | SOPS + k8s Secret | 저장소에 암호화해 두고 배포 때 푼다 |

### 3.4 인프라

DESIGN.md 9장을 그대로 쓴다. k3s 상시 노드 1대 + 필요할 때만 붙이는 노드, 워커는 KEDA로 0~N, Terraform으로 올리고 내린다. 플랫폼 공통 서비스도 워커와 같은 방식으로 배포한다. 1단계 베타는 VM 한 대(`deploy/`, docs/deploy.md)로 시작한다.

**여러 앱이 함께 도는 런타임**: 앱마다 서버를 만들지 않는다. 모든 앱의 엔진이 같은 작업 큐와 워커에서 돈다. 그래서 앱을 켜는 것은 설정 저장이고, 트래픽은 워커 수를 늘리고 줄여 받는다. 필요한 것:
- 작업마다 앱 ID를 붙이고, 앱별 동시 실행 한도(지금의 `concurrency_key`)와 LLM 예산을 둔다. 한 앱이 큐를 다 차지하지 못하게 한다.
- 같은 출처는 한 번만 수집·파싱하고 여러 앱이 같은 변경 이벤트를 받는다. 앱이 늘어도 비용이 덜 는다(RQ10).

### 3.5 엔진 틀 (엔진을 갈아 끼우는 규약)

엔진은 여러 개이고 바꿔 끼울 수 있다. 플랫폼이 어떤 엔진이든 검증·운영·보안을 대신 해 주려면, 엔진이 **"이벤트를 받아 결정을 내는"** 한 가지 모양을 지켜야 한다. 아래 코드는 방향이고, 확정은 엔진 두 개에서 한다(11장).

```python
class Engine(Protocol):
    name: str
    version: str
    consumes: list[str]  # 받는 이벤트 (예: change.detected)
    emits: list[str]  # 내는 이벤트 (예: verdict.changed)
    needs: Capabilities  # LLM 사용, 금고 범위, 도구. 선언한 것만 허용한다(7장)

    def step(self, state: State, event: Event, ctx: Context) -> Step:
        """새 상태와 낼 이벤트. LLM·도구 호출은 ctx로만 한다(게이트웨이를 지나고 녹화된다)."""
```

이 모양을 지키면 플랫폼이 대신 해 주는 것:

| 플랫폼이 해 주는 것 | 가능한 이유 |
|---|---|
| 백테스트 | 입력이 이벤트뿐이고 LLM·도구 응답이 녹화돼 있어 똑같이 다시 돌릴 수 있다 |
| 엔진·버전 비교 | 같은 이벤트를 두 엔진(또는 두 버전)에 흘려 결과 차이만 보여 준다 |
| 하네스 실험 | 게이트웨이 설정만 바꿔 다시 돌린다 |
| 배포·확장 | 상태는 DB에, 계산은 step에 있으니 워커만 늘리고 줄이면 된다 |
| 보안 | 사용자 엔진은 네트워크 없는 격리 컨테이너에서 돌고(지금 파서와 같은 방식), 밖으로 나가는 길은 게이트웨이뿐이다 |

**템플릿**: 빈 틀에서 시작하지 않게 자주 쓰는 모양을 준다. 빌더 에이전트는 템플릿을 고르고 작은 step 코드만 채운다. 목록은 초안이다.

| 템플릿 | 하는 일 | 예 |
|---|---|---|
| 변화 감시형 | 문서가 바뀌면 바뀐 부분만 처리 | 지금의 변경 영향 엔진 |
| 판정형 | 조건 → 해당/비해당 + 근거 | 자격 판정 (`eligibility/`) |
| 일정형 | 정한 시간에 행동 | 마감 알림 |
| 요약·질의형 | 문서 → 요약이나 답 (근거 인용 검사 포함) | 공고 요약 |
| 흐름형 | 여러 단계 + 사람 승인 | 신청 준비함 |

- 지금 코드(작업 큐 + 핸들러 + LLM 녹화본)는 이미 이 모양에 가깝다. 변경 영향 엔진을 틀에 맞게 옮기는 것은 틀을 뽑은 뒤에 한다.
- 4장의 도메인 팩 규약은 "변화 감시형 엔진에 붙이는 설정"으로 이 틀 아래에 들어간다.

### 3.6 빌더와 검증 (비전공자가 만드는 흐름)

1. **말하기**: "식약처 허가 사항이 바뀌면 우리 약국 재고 중 해당되는 것만 알려 줘."
2. **되묻기**: 빌더 에이전트가 선택지로 묻는다. 어느 출처(카탈로그에서), 내 목록 올리기, 어떤 변경이 중요한지.
3. **조립**: 템플릿 선택, 엔진 step 코드, 앱 설정(출처·필드·구독자·알림·민감도). 에이전트는 이 셋만 쓰고 서버나 플랫폼 코드는 만지지 않는다.
4. **미리 보기(백테스트)**: "지난 3개월이었다면 알림이 7건 이렇게 갔을 것." 사람은 카드마다 맞다/아니다를 누르고, 그 표시가 곧 이 앱의 테스트가 된다.
5. **켜기**: 설정 저장. 서버를 만들지 않는다(3.4).
6. **고치기**: "용량 변경은 빼 줘." → 기록된 사례를 전부 다시 돌려 **달라진 결과만** 보여 준다(앞서 맞다고 한 카드가 바뀌면 경고). 확인하면 적용한다.
7. **운영 보고**: 출처 장애, 파싱 실패, 비용 초과는 플랫폼이 처리하고 사람 말로 알린다("이번 주 출처가 두 번 멈췄지만 다시 받아서 놓친 것 없음").

- 백테스트에는 과거 기록이 있어야 한다. 그래서 출처는 **플랫폼이 미리 계속 모아 두는 카탈로그**에서 고른다. 카탈로그에 없는 새 출처는 오늘부터 쌓고, 그동안은 가상 변경으로 미리 본다.
- 출처마다 이용 조건(재배포 금지 등)을 카탈로그에 적고 플랫폼이 지킨다.
- 앱 범위는 처음에는 **변화 감시·판정·알림형**으로 한다. 배포를 없앨 수 있는 이유가 앱 모양이 정해져 있기 때문이다. 넓히는 것은 12장 열린 질문.

## 4. 도메인 팩 규약

도메인 팩은 아래 네 가지만 정의하면 엔진을 쓸 수 있다. 나머지(주기, 조각화, 변경 감지, 부분 재추출, 의미 기반 멈춤, 대상 계산, 발송, 근거 저장)는 엔진과 공통 서비스가 맡는다.

```python
class SourceAdapter(Protocol):
    """출처 하나. 수집 스케줄러가 부른다."""

    name: str

    def list_items(self, cursor: str | None) -> Page[ItemRef]: ...
    def fetch(self, ref: ItemRef) -> Document: ...  # 본문 + 첨부 blob 키 + 외부 ID
    def link(self, doc: Document, known: Lookup) -> str | None:
        """다른 외부 ID로 다시 올라온 같은 항목 찾기 (기업마당 재게시 등). 없으면 None."""


class FieldSpec:
    name: str  # "deadline", "eligibility_rules" ...
    type: str  # "date" | "money" | "ruleset" | "list" | 팩이 등록한 타입
    extractor: Extractor  # LLM 추출(프롬프트 + 스키마) 또는 코드 추출
    impact: Impact  # 이 필드가 바뀌면 영향받는 구독자 범위


class SubscriberModel(Protocol):
    """누가 영향을 받는가. 기본 구현은 '조건식 → SQL'."""

    def affected(self, item_id: str, changed: list[FieldChange]) -> Iterable[SubjectId]: ...
    def evaluate(self, subject: SubjectId, item_id: str) -> Verdict: ...  # 결과 + 근거


class Sink(Protocol):
    """판정 변화를 이벤트로 낸다. 기본 구현은 알림 발송 서비스로 보낸다."""

    def emit(self, event: Event) -> None: ...
```

- 구독자 모델은 바꿔 끼울 수 있어야 한다. 지원사업은 SQL 조건식, 의존성 분석은 호출 그래프 매처, 출발 알리미는 경로·정류장 교집합이다.
- **규약은 두 번째 팩을 붙일 때 확정한다.** 위 코드는 방향이고, 첫 번째 팩만 보고 일반화하지 않는다(11장).

## 5. 연동 계약

### 5.1 이벤트

모든 층이 같은 봉투를 쓴다. 1단계에서 이벤트는 버스가 아니라 DB 행(`change_event`, `job`, `outbox_alert`)이고, 큐는 PostgreSQL 작업 테이블이다.

```json
{
  "event_id": "01J...",
  "type": "verdict.changed",
  "occurred_at": "2026-11-03T09:12:00+09:00",
  "app": "apply-desk",
  "subject": "user:42",
  "item": "notice:bizinfo:PBLN_000000009000001",
  "version": 3,
  "idempotency_key": "user:42|notice:...|eligibility|v3",
  "trace_id": "4bf92f...",
  "labels": { "llm_derived": true, "citation_verified": true, "confidence": 0.92 },
  "payload": { "field": "eligibility_rules", "before": "eligible", "after": "ineligible",
               "evidence": ["lineage:42"] }
}
```

| 이벤트 | 내는 곳 | 받는 곳 |
|---|---|---|
| `document.version_created` | 수집 스케줄러 | 문서 파싱 → 엔진 |
| `change.detected` | 엔진 (조각 맞추기) | 엔진 (영향 계산), 비행 기록기 |
| `field.changed` | 엔진 (진짜 변경 판정) | 엔진 (대상 계산), 앱 |
| `verdict.changed` | 엔진 (재판정) | 알림 발송, 앱의 에이전트 |
| `alert.held` / `alert.sent` | 알림 발송 | 앱, 비행 기록기 |
| `action.held` / `action.committed` / `action.discarded` | 도구 게이트웨이 | 앱 (승인함), 비행 기록기 |

- `version`이 저장된 값보다 작으면 받는 쪽은 버린다(버전은 뒤로 가지 않는다).
- `labels`는 엔진이 붙이고 아래로 따라 흐른다. 정책은 이 레이블을 보고 판단한다(7장).

### 5.2 MCP 도구

플랫폼이 내는 범용 도구와 앱이 내는 도구를 나눈다. 모든 도구는 능력 속성을 선언한다(7장).

| 도구 | 제공 | 하는 일 | 속성 |
|---|---|---|---|
| `search_items(query, filters)` | 엔진 | 항목(공고 등) 검색 | A |
| `get_item(item_id)` | 엔진 | 항목의 현재 필드와 원문 링크 | A |
| `check(subject, item_id)` | 엔진 | 판정과 근거 | A + B |
| `watch(item_id, fields)` / `unwatch` | 엔진 | 변경 구독 | 상태 변경(내부) |
| `list_changes(since)` | 엔진 | 구독 항목의 변경 목록 | A |
| `explain(event_id)` | 엔진 | 이 변경이 왜 나에게 왔는지 근거 체인 | A + B |
| `get_profile(scope)` | 개인정보 금고 | 용도 범위 안의 프로필·서류 | B |
| `board_get` / `checklist_update` / `draft_section` | 신청 준비함 | 준비 보드 읽기·고치기 | B, 상태 변경(내부) |
| `send_inquiry(to, body)` | 신청 준비함 | 기관에 문의 메일 | **C (외부 효과)** |

A: 신뢰할 수 없는 입력, B: 민감 데이터, C: 외부 통신·되돌릴 수 없는 상태 변경.

## 6. 앱

### 6.1 신청 준비함 (1단계, 지원사업 팩)

공고 하나를 골라 신청을 마칠 때까지 같이 가는 작업 공간.

1. **내 공고**: 해당 / 거의 해당 / 확인 필요로 나뉜 목록. 판정마다 원문 근거. 시간에 따라 바뀌는 자격(예: "2026-12-01에 업력 조건을 벗어납니다")도 보여 준다.
2. **준비 보드**: 자격 체크, 제출 서류 체크리스트(올린 서류와 대조), 마감 일정(ICS), 사업계획서 초안.
3. **정정공고가 나오면**: 엔진의 `verdict.changed`·`field.changed`가 에이전트를 깨운다. 에이전트가 체크리스트·일정·초안을 고치고, 보드에 정정 전후 문단과 함께 "무엇이 왜 바뀌었는지"를 붙인다.
4. **승인함**: 에이전트가 기관에 문의 메일을 보내려는 순간(세 번째 능력)에만 승인 카드가 뜬다. 승인해도 보류 시간 동안 취소할 수 있다. 공고에 숨은 지시로 처음 보는 수신자가 끼면 게이트웨이가 표시하고 막는다.
5. **알림 근거 화면**: 알림을 누르면 조각 → 필드 → 규칙 → 판정 변화가 이어서 보인다.

DESIGN.md 1장의 비목표 중 "신청서 자동 작성"은 **초안 작성까지는 범위 안, 자동 제출은 범위 밖**으로 바꾼다.

### 6.2 후보 앱

| 앱 | 엔진에 들어가는 문서 | 구독자 모델 | 보여 주는 것 |
|---|---|---|---|
| 출발 알리미 | 운행 공지(우회·단축·막차 변경) + 실시간 위치(스트림 엔진) | 통근 경로와 정류장 교집합 | 실제 규모의 실시간 처리, 두 엔진의 조합 |
| 의존성 영향 분석 | 보안 권고, 릴리스 노트 | 저장소 호출 그래프 (그 함수를 부르는가) | 코드 도메인에서의 범용성, 수정 PR 에이전트 + 게이트웨이 |

두 번째 앱은 1단계가 끝난 뒤 하나만 고른다(10장).

빌더 단계(3.6)의 시험 앱 후보(초안): 약국(허가 사항 변경 × 재고), 학생(학사 공지 변경 × 내 수업), 임대인(법령 개정 × 내 계약), 개발자(보안 권고 × 내 코드). 직접 만들지 않고 비전공자가 빌더로 만들게 해서 RQ8을 잰다.

## 7. 위협 모델과 능력 배치

DESIGN.md 11장의 원칙(어느 구성 요소도 세 능력을 동시에 갖지 않는다)을 플랫폼 전체로 넓힌다.

| 구성 요소 | A 신뢰할 수 없는 입력 | B 민감 데이터 | C 외부 효과 | 통제 |
|---|---|---|---|---|
| 문서 파싱 | 있음 | 없음 | 없음 | 네트워크 차단 컨테이너 |
| 엔진의 추출 LLM | 있음 | 없음 | 없음 | 도구 없음, 스키마·인용 검증 |
| 엔진의 대상 계산 | 없음 | 있음 | 없음 | 결정적 코드 |
| 알림 발송 | 없음 (템플릿) | 있음 | 있음 | 아웃박스에 기록된 것만, 레이블 정책 |
| **앱의 에이전트** | **있음** | **있음** | **있음** | **도구 게이트웨이** |

에이전트만 세 능력을 모두 가지므로 게이트웨이가 아래를 강제한다.

1. **능력 선언**: 도구마다 A·B·C 속성을 선언하고 운영자가 고정한다(5.2).
2. **세션 상태**: 한번 켜진 속성은 세션이 끝날 때까지 유지한다. 상태는 사용자 단위로 이어 가서 재연결로 초기화되지 않게 한다.
3. **전이 시점 정책**: 세 번째 속성이 켜지는 호출에서만 차단·새 세션 분리·승인 중 하나를 적용한다. 나머지는 그대로 통과한다.
4. **보류 후 확정**: 승인이 필요한 효과는 묶어 두었다가 확정 때 반영한다. 메일처럼 되돌릴 수 없는 효과는 보류 시간만큼 늦춘다.
5. **범위를 줄인 토큰**: 에이전트는 개인정보 금고에서 세션 상태에 맞게 줄인 토큰으로만 B에 접근한다. 외부에서 들어온 자격증명은 통과시키지 않는다.

**빌더와 사용자 엔진**:
- 빌더 에이전트는 템플릿·엔진 step 코드·앱 설정만 쓴다. 배포·비밀값·플랫폼 코드에 닿는 도구가 없다.
- 사용자 엔진은 A(신뢰할 수 없는 입력)를 다룬다고 본다. 네트워크 없는 격리 컨테이너에서 돌고, `needs`에 선언하지 않은 능력은 쓸 수 없다. B·C가 필요하면 게이트웨이를 거친다.
- 앱 설정의 민감도 등급이 하네스(3.2)를 고른다. 만든 사람이 몰라도 기본값이 안전해야 한다.

**알림 무결성**: 에이전트가 없어도 잘못된 값 하나가 N명에게 퍼질 수 있다. 알림 발송은 레이블을 보고, **LLM에서 나왔고 인용 검증을 통과하지 못했으며 영향이 큰 변경(비해당 전환·마감 단축·금액 감소)이 N명 이상에게 가는** 경우에만 `alert.held`로 붙잡는다. 확정은 독립적인 두 번째 확인(다른 프롬프트·모델로 재추출, 안전망 비교)으로 하고, 마지막으로 운영자가 본다. 틀린 알림이 이미 나갔으면 정정 알림을 보낸다.

| RQ6 | 도구 게이트웨이(전이 시점 승인 + 보류 후 확정)는 매 행동 승인·샌드박스 단독 대비 승인 횟수와 피해 범위를 얼마나 줄이는가? | 과제당 승인 요청 수, 공격 성공 시 도달한 속성 조합, 잘못 승인된 효과 중 되돌린 건수, 승인자 정확도별 결과 |
| RQ7 | 도메인 팩이나 엔진 하나를 더하는 데 드는 비용은? 틀을 지킨 엔진은 플랫폼 코드를 고치지 않고 붙는가? | 팩·엔진 코드 줄 수, 플랫폼 변경 줄 수, 추가에 든 시간 |
| RQ8 | 비전공자가 코드를 보지 않고 백테스트·비교 화면만으로 잘못된 앱 변경을 잡아내는가? | 일부러 버그를 심은 변경 과제에서 잡아낸 비율, 잘못 승인한 비율, 미리 보기만 준 조건과 비교 |
| RQ9 | 하네스는 민감 데이터 유출과 인젝션을 얼마나 줄이고, 정확도·비용을 얼마나 잃는가? | 하네스 켬/끔별 유출 건수, 인젝션 성공률, 라벨 대비 정확도, 토큰·지연 |
| RQ10 | 같은 출처를 여러 앱이 함께 쓰면 앱 수에 따라 비용이 어떻게 느는가? | 앱 N개일 때 수집·파싱·LLM 비용, 앱별로 따로 돌릴 때와 비교 |

- RQ6 평가에는 **실제 공고·HWP에 인젝션을 심은 과제 세트**를 만든다(AgentDojo의 도메인 특화판). 공개 산출물 후보다.
- 각 질문은 데이터가 쌓이는 단계(10장)에서 측정한다.

## 9. 저장소 구성

혼자 개발하는 동안은 **이 저장소 하나에서 패키지로 나눈다.** 저장소를 여러 개로 나누면 규약을 바꿀 때마다 여러 곳을 맞춰야 한다.

```text
src/noticedelta/
  core/              엔진과 공통 서비스 (지금 모듈 대부분이 여기로)
  packs/grants/      지원사업 팩 (출처 어댑터, 속성 사전, 필드 정의, 프롬프트)
  apps/apply_desk/   신청 준비함 (API, 에이전트)
gateway/             도구 게이트웨이 (규약이 굳으면 별도 저장소로 뗀다)
web/                 앱 화면
```

- 패키지 이동은 1단계 끝(두 번째 팩을 붙이기 직전)에 한 번에 한다. 그 전에는 지금 구조를 유지한다.
- 도구 게이트웨이는 다른 MCP 서버 앞에도 쓸 수 있는 범용 프록시라서, 규약이 굳으면 따로 공개한다.

## 10. 단계

단계는 **완료 기준**으로 넘어간다. 기간은 초안이고, 바꿀 때는 아래 표의 "기간(초안)" 열만 고친다.

| 단계 | 기간(초안) | 할 일 | 완료 기준 |
|---|---|---|---|
| 1. 지원사업 앱 | ~2026-12-14 (확정) | DESIGN.md 14장. 상시 수집, 사람 라벨 평가셋, 사업 단위 데이터 모델, PG 작업 큐, 판정 화면, ICS 알림, VM 배포, 비공개 베타 | 베타 5~10명, 실제 정정 재생 데모, RQ1 측정 동결 |
| 2. 게이트웨이와 하네스 | 2027-01~02 | 신청 준비함, 신청 에이전트, 개인정보 금고, 도구 게이트웨이, MCP 서버, 승인함, 입력·출력 하네스(3.2). 인젝션 과제 세트는 가상 공고로 만든다 | 정정공고 → 에이전트가 보드 갱신 → 문의 메일이 보류 후 확정되는 장면, RQ6·RQ9 파일럿 |
| 실운영 | 2027-02~03 | 지원사업 시즌에 맞춘 실사용자 운영 | 사용자 지표 |
| 3. 두 번째 엔진과 틀 | 2027-03~04 | 다른 템플릿 모양의 두 번째 엔진·도메인을 손으로 만든다(후보: 나라장터 입찰 정정, 출발 알리미, 의존성 영향 분석). 두 엔진에서 틀 v1을 뽑고 변경 영향 엔진을 옮긴다. 패키지 이동(9장) | 두 번째 엔진이 플랫폼 코드를 거의 고치지 않고 돈다(RQ7) |
| 4. 검증 | 2027-05~06 | 백테스트, 엔진·버전 비교, 하네스 실험 화면. 틀을 지킨 엔진이면 모두 쓸 수 있게 | 두 엔진 모두에서 "바꾸면 달라진 결과만" 화면이 돈다 |
| 5. 빌더 | 2027-07~09 | 빌더 에이전트, 템플릿, 출처 카탈로그, 사용자 엔진 격리 실행 | 비전공자가 개발자 도움 없이 앱 하나를 만들어 켠다 |
| 6. 함께 도는 런타임과 측정 | 2027-10~12 | 여러 앱 런타임(앱별 한도·예산), k3s·KEDA·Terraform, 관측, 부하 시험, 비전공자 사용성 실험, 공개 데이터셋(해시·라벨) | RQ8·RQ10 측정, `make eval`로 실험표 재현 |

**밀리면 줄이는 순서** (뒤 단계부터 줄이고, 완료 기준은 지킨다):
1. 6단계의 k3s·Terraform → VM 한 대 + 워커 수 조절로 대신한다.
2. 5단계의 템플릿 수 → 변화 감시형·판정형 둘만.
3. 5단계의 출처 카탈로그 → 이미 모으는 출처만.
4. 4단계의 하네스 실험 화면 → 명령어 한 줄과 표로 대신한다.

## 11. 결정 원칙

- **동작하는 것에서 뽑아낸다.** 엔진의 범용 규약은 첫 번째 앱이 실제 데이터로 끝까지 돈 다음, 두 번째 팩을 붙이면서 정한다.
- **차별점이 없는 것은 가져다 쓴다.** 인증·검색·관측·비밀값은 표준 부품이다(3.3).
- **층 사이는 이벤트와 MCP로만.** 앱은 엔진 테이블을 직접 읽지 않는다.
- **LLM은 구독자를 보지 않는다.** 구독자별 계산은 코드로 한다. 비용(RQ1)과 보안(7장)이 같은 결론을 낸다.
- **세 능력이 모이는 곳은 하나로.** 앱의 에이전트만 세 능력을 갖고, 그 앞에는 반드시 게이트웨이가 있다.
- **앱은 서버가 아니라 설정이다.** 앱마다 서버를 만들지 않는다. 배포·확장·백업은 플랫폼 하나의 일이다.
- **틀을 지킨 엔진만 플랫폼이 운영한다.** 이벤트 → 결정 모양, 능력 선언, 부수 효과는 게이트웨이로. 이것이 갈아 끼우기·검증·자동 운영을 함께 가능하게 한다. 틀은 엔진 두 개에서 뽑는다.
- **확인은 결과로 한다.** 만든 사람에게 코드를 보여 주지 않고, 바꾸기 전후의 달라진 결과를 보여 준다.
- **기본값이 안전해야 한다.** 만든 사람이 보안을 몰라도 민감도 등급만으로 하네스가 켜진다.
