| 항목 | 내용 |
|---|---|
| 상태 | **초안.** 부품마다 만들 때 확정한다. |
| 작성일 | 2026-11-18 |
| 관계 | ARCHITECTURE 3.2(공통 부품), 5장(연동 계약), 7장(위협 모델)을 구체화한다. 앱 정의(app-spec.md), 출처 카탈로그(source-catalog.md)와 맞물린다. **플랫폼 전체의 만드는 순서는 이 문서 8장이 기준이다.** |

## 0. 한 줄

네 부품은 한 가지 질문에 나눠 답한다. **무슨 일이 왜 일어났고, 누가 무엇을 볼 수 있으며, 무엇을 해도 되는가.**

| 부품 | 맡는 질문 |
|---|---|
| **이벤트 봉투** | 층 사이에 무슨 일이 일어났나 (모두 같은 모양으로) |
| **비행 기록기** | 왜 그렇게 됐나. 다시 돌리면 같은가. 바꾸면 어떻게 되나 |
| **개인정보 금고** | 누가 어떤 개인정보를 어떤 용도로 볼 수 있나 |
| **도구 게이트웨이** | 에이전트가 무엇을 해도 되나 |

그리고 넷 위에 고리 하나를 얹는다. **에이전트가 쓴 기록으로 도구를 계속 고친다**(10장).

쌓이는 순서도 이렇다. 봉투가 바닥(모두가 쓰는 말)이고, 기록기는 봉투와 바깥과의 경계를 묶고, 금고는 민감 데이터를 맡고, 게이트웨이는 셋 위에서 에이전트를 통제한다.

## 1. 네 부품이 함께 쓰는 약속

### 1.1 주체 (누가)

| 주체 | 모양 | 예 |
|---|---|---|
| 사람 | `person:<ULID>` | 앱을 쓰는 사람, 앱을 만든 사람 |
| 앱 | `app:<id>@<판>` | `app:grant-alerts@3` |
| 에이전트 세션 | `session:<ULID>` | 사람 하나·앱 하나의 대화 |
| 플랫폼 부품 | `svc:<이름>` | `svc:collector`, `svc:engine`, `svc:notify` |

- **예전의 문제** (2026-11-24 고침): 개인 링크의 비밀 토큰이 곧 사용자 ID(`profile.user_id`)였고, 판정·구독·알림(멱등 키와 본문 포함)에도 그 값이 그대로 들어갔다. 비밀이 DB 곳곳에 평문으로 퍼져 있었다. 지금은 사람 ID(`person`)를 따로 두고, 링크는 토큰의 sha256 해시만 저장한다(`access_link`, `people.py`, 마이그레이션 0009). 결과 테이블의 칸은 `person_id`다.

### 1.2 능력 속성 A·B·C

ARCHITECTURE 7장 그대로다. A는 신뢰할 수 없는 입력(외부 문서, 남이 쓴 글), B는 민감 데이터(개인정보), C는 밖으로 나가거나 되돌릴 수 없는 효과다. 한 세션이 셋을 동시에 갖게 되는 순간을 통제한다. 같은 생각을 Meta의 "Agents Rule of Two"(2025)와 "lethal trifecta"가 다룬다.

### 1.3 레이블 (값이 어디서 왔나)

값마다 붙어 흐르는 표시다. 봉투의 `labels`, 기록기의 기록, 게이트웨이의 판단이 같은 이름을 쓴다.

| 레이블 | 뜻 | 붙이는 곳 |
|---|---|---|
| `untrusted` | 외부 문서·사람이 쓴 글에서 왔다 (A) | 수집, A 도구의 결과 |
| `sensitive` | 개인정보에서 왔다 (B) | 금고 |
| `llm_derived` | LLM이 뽑았다 | 추출 |
| `citation_verified` | 인용 검증을 통과했다 | 추출 |
| `confidence` | 0~1 | 추출, 판정 |

레이블은 값을 합칠 때 넓어지기만 한다(합집합). 사람의 확인(승인)만이 `untrusted`를 뗄 수 있다.

### 1.4 추적

- **trace**: 하나의 일 묶음. 수집 실행 하나, 파이프라인의 한 줄기, 에이전트 세션 하나, 미리 돌려 보기 한 번.
- 모든 봉투와 기록은 `trace_id`와 원인(`causation_id`: 이 일을 일으킨 봉투)을 단다. "이 알림은 어느 수집의 어느 변경에서 왔나"를 거꾸로 따라갈 수 있다. 지금 화면의 "알림 근거"를 플랫폼 전체로 넓힌 것이다.

### 1.5 시간과 판

- `occurred_at`(일어난 때)과 `recorded_at`(기록한 때)을 나눈다. 재생할 때는 기록된 시각을 쓴다(지금도 코드가 `now`를 주입받는다).
- 판이 있는 것은 함께 남긴다: 항목 판, 앱 판, 플랫폼 판(커밋), 하네스·모델 설정의 해시. 회귀 시험이 "어느 판으로 계산했나"를 알아야 하기 때문이다.

## 2. 이벤트 봉투

### 2.1 왜

- 지금은 `change_event`, `field_value`, `judgment`, `outbox_alert`, `source_drift`가 각자 다른 모양이다. 엔진을 갈아 끼우거나(ARCHITECTURE 3.5) 앱이 일을 구독하려면 같은 모양이 필요하다.
- 기록기가 한 줄기로 쌓고 다시 흘리려면 같은 모양이 필요하다.

### 2.2 모양 (ARCHITECTURE 5.1을 다듬음)

```json
{
  "id": "01JD7Q4K2M...",
  "type": "verdict.changed",
  "v": 1,
  "occurred_at": "2026-11-18T09:12:00+09:00",
  "recorded_at": "2026-11-18T09:12:03+09:00",
  "producer": "svc:engine",
  "app": "app:grant-alerts@3",
  "subject": "person:01JC...",
  "item": "item:01HZ...",
  "item_version": 4,
  "trace_id": "01JD7Q3...",
  "causation_id": "01JD7Q4J...",
  "idempotency_key": "person:01JC|item:01HZ|eligibility_rules|v4",
  "labels": {"llm_derived": true, "citation_verified": true, "confidence": 0.92},
  "payload": {"field": "eligibility_rules", "before": "eligible", "after": "ineligible",
              "evidence": ["lineage:L42"]}
}
```

- `id`는 ULID라 시간 순으로 정렬된다.
- `v`는 그 타입의 판이다. 타입마다 따로 올린다.
- `app`, `subject`, `item`은 해당될 때만 채운다. 예를 들어 `source.run_finished`에는 셋 다 없다.

### 2.3 규칙

1. **추가만 한다.** 고칠 일은 새 봉투로 남긴다(예: `alert.corrected`).
2. **상태 변경과 봉투 쓰기는 한 트랜잭션이다**(트랜잭셔널 아웃박스). 지금 작업 큐가 "결과 기록과 다음 작업 등록을 한 트랜잭션"으로 하는 것과 같은 방식이다.
3. **순서**: 같은 항목의 봉투는 `item_version`이 줄지 않는다. 받는 쪽은 이미 본 판보다 작은 판을 버린다.
4. **한 번만**: `(type, idempotency_key)`는 유일하다. 받는 쪽도 봉투 `id`로 중복을 거른다. 전달은 "최소 한 번", 처리는 멱등이다.
5. **개인정보 값을 넣지 않는다.** `subject`는 ID만 쓴다. `payload`에는 판정 결과는 넣어도 되지만 "창업일 2021-01-01" 같은 B 값은 넣지 않는다. 필요하면 금고 참조를 넣는다.
6. **원문 인용은 짧게**: 출처 이용 조건의 노출 한도(source-catalog.md의 `terms.quote_limit`)를 따른다.
7. **타입 등록부**: 타입마다 `payload` 스키마(JSON Schema)와 판을 코드에 둔다. 모르는 타입이나 스키마에 맞지 않는 봉투는 쓰지 않는다. 스키마를 바꾸면 `v`를 올리고, 받는 쪽은 한동안 두 판을 다 읽는다.

### 2.4 1차 타입

| 타입 | 내는 곳 | 지금 남는 곳 |
|---|---|---|
| `source.run_finished` | 수집 | `runs/*.json`, `last_run.json` |
| `source.drift_held`, `source.drift_decided` | 형식 변화 감시 | `source_drift` |
| `document.version_created` | 적재 | `notice_version`, `program_version` |
| `document.parsed` | 파싱 | `attachment.parse_status` |
| `change.detected` | 엔진 | `change_event` |
| `field.changed` | 엔진 | `field_value` |
| `verdict.changed` | 엔진 | `judgment` |
| `alert.created` · `held` · `released` · `sent` · `corrected` · `superseded` · `discarded` | 알림 발송 | `outbox_alert.status` |
| `app.version_enabled` | 앱 정의 | (앱 정의 2단계에서 생김) |
| `consent.granted`, `consent.withdrawn` | 금고 | `profile`의 동의 칸 |
| `action.requested` · `held` · `approved` · `committed` · `discarded` · `blocked` | 게이트웨이 | 없음 |

### 2.5 전달

- **메시지 버스를 두지 않는다**(DESIGN 9.3). 봉투는 PostgreSQL `event` 테이블에 쌓는다. 구독(받는 쪽, 타입 패턴, 앱 거르기)마다 지금의 작업 큐에 작업을 넣는다(`dedupe_key` = 봉투 id + 받는 쪽). 재시도, 임대, 실패 처리는 작업 큐에 이미 있다.
- **처음에는 같이 쓴다.** 지금 테이블은 그대로 두고 봉투를 함께 쓴다. 받는 쪽을 하나씩 봉투로 옮기고, 지금 테이블은 화면이 읽는 모델(projection)로 남긴다.
- **크기**: `payload`는 64KB 이하. 조각 목록처럼 큰 것은 원문 저장소의 키만 넣는다.

### 2.6 만든 것 (2026-11-25)

`events.py`, 표 `event`(마이그레이션 0012). 위 1차 타입 가운데 `action.*`(게이트웨이)을 뺀 것을 모두 낸다.

| 봉투 | 내는 곳 |
|---|---|
| `source.run_finished`, `document.version_created` | 적재 작업 (`pipeline.handle_load`) |
| `document.parsed` | 파싱 작업 |
| `change.detected` | 비교 작업 |
| `field.changed`, `verdict.changed`, `alert.created`, 근거 부족 `alert.held` | 영향 계산 작업 |
| `alert.superseded` · `discarded` · 대량 영향 `held` · `released` · `sent` · `corrected` | 알림 발송(`notify`) |
| `source.drift_held`, `source.drift_decided` | 형식 변화 감시(`drift`) |
| `app.version_enabled` | 앱 정의(`app_registry.enable`) |
| `consent.granted`, `consent.withdrawn` | 동의(`web/consent`) |

- **추적**: 작업 본문에 `trace`(묶음)와 `cause`(원인 봉투)를 실어 다음 작업으로 넘긴다. 수집 실행 하나가 묶음이 되고, 보낸 알림에서 원인을 거꾸로 따라가면 `alert.sent ← alert.created ← verdict.changed ← change.detected ← document.parsed ← document.version_created ← source.run_finished`로 끊기지 않는다(`tests/test_events.py`).
- **구독**: 코드에 둔다(`events.subscribe`). 9장의 "작업 큐로 할까"를 작업 큐로 정했다. 첫 구독은 알림 발송이다. 영향 계산이 알림 발송 작업을 직접 넣던 것을 `alert.created` 구독으로 바꿨다(항목 판 하나에 한 번).
- **같이 쓰기**: 지금 표(`change_event`, `field_value`, `judgment`, `outbox_alert`, `source_drift`)는 그대로 쓰고 봉투를 함께 쓴다(2.5).
- **ULID**는 같은 밀리초 안에서도 순서를 지키도록 1씩 올린다(같은 작업 안에서 낸 봉투의 순서).
- **아직 안 한 것**: 판이 바뀐 타입의 두 판 읽기(2.3의 7번), DB에 둔 구독 표(`event_subscription`), `action.*`.

## 3. 비행 기록기

### 3.1 왜

| 쓰임 | 뜻 |
|---|---|
| 감사 | 누가 어떤 데이터를 어느 모델·도구에 보냈나 |
| 재생 | 같은 입력이면 같은 결과가 나오나. 바꾸면 무엇이 달라지나. 미리 돌려 보기, 비교, 플랫폼 회귀 시험, 하네스 실험이 모두 이 위에 선다 |
| 설명 | 이 알림은 왜 나에게 왔나 |

### 3.2 무엇을 기록하나

원칙: **결정적이지 않은 것은 모두 경계를 지날 때 기록한다.** 경계 안쪽 코드는 결정적이라 같은 입력이면 같은 결과가 나온다.

| 경계 | 기록하는 것 | 지금 |
|---|---|---|
| 출처(수집) | 실행 파일과 원문 | `runs/`, `blobs/`에 있음 |
| 파서 | 원문 키, 파서 판, 출력의 해시 | `record(kind=parse)` + 파싱 결과는 원문 저장소(2026-11-25) |
| LLM 호출 | 하네스를 거친 요청, 응답, 모델, 토큰, 비용, 하네스가 찾은 것 | 녹화본(cassette)에 있음. 색인은 `record(kind=llm_call)`(2026-11-25) |
| 도구 호출 | 도구, 인자(B 값은 금고 참조로), 결과 요약, 게이트웨이 판단, 세션 상태 | 없음 |
| 금고 접근 | 누가, 어느 용도로, 어떤 키를 (값은 아님) | 없음 |
| 시계·무작위 | 기준 시각, 씨앗 | 주입은 있음. 작업 큐의 등록 시각은 아직 실제 시계(3.7) |
| 사람의 판단 | 승인, 라벨, 형식 변화 결정 | `label`, `source_drift`에 흩어져 있음 |
| 판 | 플랫폼 커밋, 앱 판, 하네스·모델 설정의 해시 | `trace.platform_rev`, `config_hash`(2026-11-25) |

봉투(2장)는 그 자체로 기록이다. 기록기는 봉투를 베끼지 않고 trace로 엮기만 한다.

### 3.3 모양

- `trace(id, kind, parent_id, started_at, ended_at, platform_rev, app, config_hash, status)`
  - `kind`: `collect_run` · `pipeline` · `agent_session` · `backtest` · `eval` · `regression`
- `record(id, trace_id, seq, kind, at, ref, digest, cost, payload)`
  - `kind`: `event` · `llm_call` · `tool_call` · `vault_access` · `decision`
  - `ref`: 봉투 id, 녹화본 키, 원문 키 가운데 하나
  - `digest`: 입력·출력의 해시. 재생 결과와 비교할 때 쓴다
  - `payload`: 작게, 가린 것만
- LLM 입출력처럼 큰 내용은 지금처럼 녹화본 저장소에 해시 키로 두고, `record`에는 키만 넣는다.

### 3.4 재생

- **같게 재생**: 같은 코드·설정으로 기록된 입력을 다시 흘리면 출력의 `digest`가 같아야 한다. 다르면 결정적이지 않은 곳이 새는 것이고, 버그다.
- **바꿔 재생**: 앱 판, 하네스, 모델, 엔진, 플랫폼 판 가운데 하나를 바꿔 같은 입력을 흘리고 출력 차이를 본다. 미리 돌려 보기(app-spec 10.1), 비교(10.2), 플랫폼 회귀 시험(app-spec 15장), 평가 틀(`make eval`)이 모두 이것이다.
- **재생할 때 C 도구는 실행하지 않는다.** 기록된 결과를 돌려준다. 외부 효과가 두 번 나가지 않게 하기 위해서다. 기록이 없으면 "기록 없음"으로 멈춘다(평가 틀의 "녹화본 없음"과 같다).
- 원문이 저장소에 없으므로 재생은 CI가 아니라 로컬이나 서버에서 돈다.

### 3.5 개인정보와 보관

- **기록에 B 값을 넣지 않는다.** 도구 인자의 개인정보는 금고 참조(`vault:<허가>/<키>`)로 바꿔 적는다. LLM 요청은 하네스가 이미 가린 것이다(앱의 민감도가 `personal` 이상일 때).
- **보관**: 기록은 앱의 보관 기한을 따른다. 사람을 지우면(4.6) 그 사람의 금고 값이 지워지고, 기록에는 사람 ID만 남는다(가명).
- **한계**: 가명 ID만 남은 기록도 다른 정보와 붙이면 사람을 알아볼 수 있다. 그래서 보관 기한이 지나면 기록 자체를 지운다.

### 3.6 지금 것과의 관계

- 녹화본(`FileCassetteStore`)은 저장소로 그대로 쓰고, 기록기가 그 위에 색인을 단다.
- 평가 틀(`evaluation`)은 기록기에서 이벤트를 고르게 바뀐다.
- 형식 변화 결정과 라벨은 `decision` 기록으로 묶인다.

### 3.7 만든 것 (2026-11-25)

`flight.py`(공통), `replay.py`(앱), 표 `trace`·`record`(마이그레이션 0013), `scripts/replay.py`.

- **묶음**: 적재 작업이 수집 실행 하나마다 `collect_run` 묶음을 연다.
  - id는 그 실행의 첫 봉투(`source.run_finished`) id와 같다. 봉투는 이미 `trace_id`로 엮여 있으므로 베끼지 않는다.
  - 묶음에는 플랫폼 판(git 커밋, 고친 것이 있으면 `+dirty`)과 설정을 적는다. 설정은 앱 판, 비교기 판, 파서, 추출기다.
- **기록**: 파서를 실제로 부른 호출은 `parse`로 남긴다. 캐시에서 꺼낸 것은 파서를 부르지 않으므로 남지 않는다. 남기는 것은 원문 키, 출력 해시, 파서 판이다.
  - 게이트웨이에 관찰자(`observer=flight.llm_observer`)를 달면 LLM 호출이 `llm_call`로 남는다. 남기는 것은 녹화본 키, 출력 해시, 토큰이다.
  - 작업을 처리하는 동안 `flight.bound`로 묶음을 걸어 둔다. 파싱과 영향 계산 작업이 그렇게 한다.
- **닫기와 해시**: 워커는 일을 마칠 때 남은 작업이 없는 묶음을 닫는다. 닫을 때 출력의 정규형 해시(`trace.digest`)를 적는다.
  - 정규형은 묶음의 봉투에서 ID를 자연 키(출처/게시물 번호/판 번호)로 바꾸고, 시각을 뺀 줄들이다.
  - 작업을 꺼낸 순서와 무관하게 비교하려고 줄을 정렬한다.
- **같게 재생**: `scripts/replay.py`는 빈 DB에 `runs/`의 실행을 처음부터 다시 흘린다. 실행마다 해시를 내서, 기록된 해시나 한 번 더 재생한 결과와 비교한다.
  - 원문 저장소는 읽기만 한다.
  - 파서 대신 원래 DB의 파싱 결과를 쓴다. 없으면 그 작업만 "기록 없음"으로 멈춘다.
  - 형식 변화 결정은 결정한 시각 뒤의 실행부터 같은 결정을 적용한다.
  - 비교에서 파서는 설정에서 뺀다. 기록으로 바꿨기 때문이다.
- **바꿔 재생**: 입력(파싱 결과)이나 설정을 바꿔 다시 흘리면 해시가 달라진다. 어느 봉투가 다른지 줄 단위로 나온다(`replay.compare`). 테스트가 이것을 확인한다.
- **기록기가 찾은 누수**: 작업 큐는 작업을 등록할 때 주입한 시계가 아니라 실제 시계를 쓴다(`jobs.enqueue`의 기본값).
  - 그래서 재생 시계를 과거 날짜에 두면 작업을 꺼내지 못하고 순서가 섞였다.
  - 지금은 재생 시계를 "지금 + (그 실행 시각 - 첫 실행 시각)"으로 두어 피한다. 시각은 해시에 넣지 않는다.
  - 고치려면 파이프라인이 `enqueue`에 시계를 넘겨야 한다.
- **아직 안 한 것**:
  - 사람의 판단(라벨, 형식 변화 결정)을 `decision` 기록으로 묶기. 지금은 재생이 `source_drift` 표를 직접 읽는다.
  - 봉투 밖의 상태(필드 값, 판정)까지 해시에 넣기.
  - 운영 워커에 추출기를 붙일 때 게이트웨이에 관찰자 달기.

## 4. 개인정보 금고

### 4.1 왜

- 민감 데이터(B)를 한곳에 모으고, **용도별 동의 안에서, 범위를 줄인 허가로만** 꺼내게 한다.
- 지금의 문제는 셋이다.
  - 프로필 속성이 앱 테이블(`profile`)에 있다.
  - 비밀인 링크 토큰이 사용자 ID로 퍼져 있다(1.1).
  - 동의가 앱 하나, 용도 하나뿐이다.

### 4.2 담는 것

| 담는 것 | 모양 | 예 |
|---|---|---|
| 사람 | `person(id, created_at, deleted_at)` | |
| 들어오는 길 | `access_link(token_hash, person_id, created_at, last_used_at, revoked_at)` | 개인 링크. **토큰 원문은 저장하지 않는다** |
| 속성 값 | `vault_value(person_id, key, value, source, updated_at, expires_at)` | 창업일, 지역, 매출. `source`: 직접 입력 / 계산 / 서류에서 |
| 서류 | `vault_document(id, person_id, blob_key, kind, uploaded_at, expires_at)` | 사업자등록증 사본(신청 준비함) |
| 동의 | `consent(person_id, app, purpose, keys, text_version, granted_at, withdrawn_at)` | |
| 허가 | `vault_grant(id, person_id, app, purpose, keys, holder, expires_at, uses)` | `holder`: 세션 또는 플랫폼 부품 |

- 속성 값은 **사람 단위로 한 번** 둔다. 여러 앱이 같은 창업일을 쓰기 때문이다. 어느 앱이 어느 키를 읽을 수 있는지는 동의가 정한다.
- 속성의 이름과 타입은 앱 정의(`subjects.attributes`)가 정하고, 금고는 그 키로 값을 담는다.

### 4.3 용도

| 용도 | 누가 | 무엇을 |
|---|---|---|
| `judge` (판정) | `svc:engine` | 앱이 판정에 쓰는 키. 대량 판정 SQL이 금고의 뷰를 읽는다. LLM에는 가지 않는다 |
| `notify` (알림) | `svc:notify` | 받을 곳(이메일 등) |
| `assist` (에이전트 도움) | 에이전트 세션 | 신청 준비함이 쓰는 키와 서류. **게이트웨이를 거쳐서만** |
| `research` (연구) | 연구 스크립트 | 선택 동의한 사람의 가명 통계만 |
| `self` (본인) | 본인의 링크 | 자기 것 전부 |

### 4.4 허가 (범위를 줄인 토큰)

- 금고에서 값을 꺼내려면 허가가 있어야 한다. 허가는 (사람, 앱, 용도, 키 목록, 가진 쪽, 만료)이다. 동의 범위를 넘는 허가는 만들 수 없다.
- **에이전트는 허가를 직접 받지 않는다.** 게이트웨이가 세션 상태를 보고(5.4) 그 도구가 필요한 만큼만 허가를 받아 도구를 실행한다. 에이전트에게는 값만, 그 도구가 필요한 것만 간다.
- 꺼낼 때마다 기록기에 `vault_access`를 남긴다(키 이름, 용도, 허가 id. 값은 아님).

### 4.5 지키는 방법

- **값은 애플리케이션 단에서 암호화해 저장한다.** 키는 환경 변수에 두고, 나중에 KMS로 옮긴다. DB 덤프나 백업이 새도 값은 읽히지 않는다. 서버 자체가 뚫리면 지키지 못한다는 점은 정직하게 적어 둔다.
- PostgreSQL 행 수준 보안(RLS)으로 금고 테이블은 금고 코드의 DB 역할만 읽게 할 수 있다(다음 단계).
- **서류 파일은 공고 원문 저장소와 섞지 않는다.** 사람마다 따로 두고, 같은 파일이어도 합치지 않는다. 내용 해시를 공유하면 "다른 사람도 같은 서류를 올렸다"는 사실이 드러나기 때문이다.
- **받지 않는 것**: 주민등록번호 같은 고유식별정보(DESIGN 11장). 사업자등록번호는 선택 입력이다.

### 4.6 보관과 지우기

- 값마다 보관 기한이 있다(앱 정의의 보관 기간, 베타 종료일 등). 기한이 지난 값을 지우는 작업이 하루 한 번 돈다.
- **본인이 지우면** 값, 서류, 허가, 링크를 지우고 동의 철회만 남긴다(무엇을 언제 철회했는지). 사람 ID는 남는다. 봉투와 기록의 가명 ID다.
- **동의를 철회하면** 그 앱·용도의 허가가 바로 무효가 되고, 그 앱의 판정과 알림이 멈춘다.

### 4.7 지금 것에서 옮기기

| 지금 | 금고에서 |
|---|---|
| `profile.user_id`(토큰 원문) | `person` + `access_link`(토큰 해시). 판정·구독·알림의 `user_id`는 `person_id`로 |
| `profile.attributes` | `vault_value` |
| `consent_version`, `consented_at`, `research_ok` | `consent` (앱 `grant-alerts`, 용도 `judge`·`notify`, 선택 `research`) |
| `web/consent.py`의 "내 정보 지우기" | 금고의 지우기(4.6) |

## 5. 도구 게이트웨이

### 5.1 왜

에이전트는 A·B·C를 모두 가질 수 있는 유일한 주체다(ARCHITECTURE 7장). 게이트웨이는 **에이전트의 모든 도구 호출이 지나는 유일한 길**이다. MCP 서버도 그 뒤에 선다.

### 5.2 도구 선언 (지금의 `tooling.Tool`을 넓힘)

| 칸 | 뜻 |
|---|---|
| `capabilities` | A·B·C |
| `effect` | `none` / `internal`(플랫폼 안의 되돌릴 수 있는 상태: 체크리스트 고치기) / `external`(메일, 웹훅, 앱 켜기) |
| `undo` | 되돌리는 도구. `internal`에만 있다 |
| `purpose`, `keys` | B 도구가 금고에서 쓰는 용도와 키 |
| `hold` | C 효과를 붙잡아 두는 시간(취소할 수 있는 시간) |
| `targets` | C 도구의 받는 쪽 칸(받는 사람, 주소)과 허용 목록 |
| `limits` | 세션·앱별 호출 수, C 효과 수 |

선언은 코드에 두고 운영자가 고정한다. 앱 정의는 이것을 바꿀 수 없고, 쓸 도구를 고르기만 한다.

### 5.3 세션

- `session(id, person, app, agent, flags, started_at, last_seen_at, status)`. `flags`는 {A, B, C}.
- 세션은 사람·앱·대화 단위로 이어진다. **다시 접속해도 `flags`가 초기화되지 않는다**(ARCHITECTURE 7장 2번).
- `flags`는 켜지기만 한다. A를 돌려주는 도구를 부르면 A, 금고에서 읽으면 B, C 효과가 확정되면 C가 켜진다.

### 5.4 판단

호출마다 게이트웨이가 차례로 본다.

1. **선언**: 등록된 도구인가, 앱이 쓰기로 고른 도구인가, 한도 안인가.
2. **동의와 허가**: B 도구면 금고에 이 세션·용도로 허가를 받는다. 동의 밖이면 막는다.
3. **전이**: 이 호출로 세션이 A·B·C를 모두 갖게 되면(세 번째가 켜지는 순간) 정책을 적용한다. 그 밖의 호출은 그대로 통과한다.

   | 정책 | 하는 일 | 기본으로 쓰는 곳 |
   |---|---|---|
   | `approve` | 사람의 승인을 받는다 | `external` 효과 (메일 보내기) |
   | `split` | 외부 글을 보지 않은 새 세션이 정해진 서식으로만 만든다 | 서식이 정해진 효과 (기관 문의 메일을 템플릿 칸으로) |
   | `block` | 막는다 | 앱이 고르지 않은 C, 한도 초과 |

4. **받는 쪽 검사**: C 도구의 받는 쪽이 허용 목록에 없거나, 신뢰할 수 없는 글(A)에서만 본 값이면(예: 공고 본문에 숨어 있던 이메일 주소) 표시하고 기본으로 막는다. 승인이 있어도 표시는 남긴다.
5. **기록**: 판단과 이유를 기록기에 남긴다.

### 5.5 보류 후 확정

- C 효과는 바로 실행하지 않고 `action`으로 만든다.
  `requested → held → approved → committed`, 또는 `discarded` · `expired` · `blocked`
- **승인한 뒤에도 보류 시간 동안 취소할 수 있다.** 메일처럼 되돌릴 수 없는 효과를 위해서다. 되돌릴 수 있는 `internal` 효과는 바로 반영하고 되돌리기 방법을 기록한다.
- **승인함**: 사람에게 보이는 카드에는 무엇을, 누구에게, 무엇을 근거로(이 세션이 본 외부 글 가운데 어떤 것이 영향을 줬는지), 언제 나가는지를 보여 준다. 승인, 거절, 고치기를 고를 수 있다.
- 게이트웨이는 `action.*` 봉투를 낸다. 알림 발송의 붙잡기(`alert.held`)와 같은 모양이다.

### 5.6 비밀값

C 도구가 쓰는 계정과 토큰(메일 계정 등)은 게이트웨이만 갖고, 에이전트에게 주지 않는다. 에이전트가 건네는 자격증명은 받지 않는다(ARCHITECTURE 7장 5번).

### 5.7 앱을 만드는 에이전트에도 같은 길

app-spec 3장의 "사람의 확인이 꼭 필요한 순간"(앱 켜기, 판 바꾸기, 출처 등록, 밖으로 나가는 채널, 예산 올리기)은 조종 도구를 `external` 효과로 선언해서 같은 승인을 거치게 한다. 따로 만들지 않는다.

### 5.8 MCP와의 관계

- 지금의 등록부(`tooling.Registry`: A 도구만 내놓기)가 게이트웨이의 첫 판이다. 게이트웨이가 생기면 B·C 도구도 내놓되, 위 판단을 거친다.
- MCP 접속에는 주체가 있어야 한다. 지금은 로컬 stdio라 주체가 운영자 한 사람이다. 원격 MCP(다른 사람의 에이전트)는 인증(OAuth)이 붙은 뒤에 연다.

### 5.9 한계

- **세션 단위 표시는 거칠다.** 외부 글을 한 번 본 세션은 끝까지 A다. 그래서 승인 요청이 늘 수 있다. RQ6이 승인 횟수와 피해 범위를 잰다.
- 인자 하나하나의 출처를 정확히 따지려면 에이전트의 계획과 데이터를 분리해야 한다(예: Google DeepMind의 CaMeL 같은 방식). 1차에서는 받는 쪽 칸만 따진다.

| 7 | 에이전트가 문의 메일을 보내려 함 | `action.requested` → `action.held` | 판단 기록 | | 세 번째(C)가 켜지는 순간 → `approve`. 받는 사람이 공고 본문에서만 본 주소면 표시하고 막음 |
| 8 | 사람이 승인, 10분 뒤 나감 | `action.approved` → `action.committed` | T1에서 메일까지 원인 사슬이 이어짐 | | 보류 시간 동안은 취소 가능 |

**재생**: 같은 기록을 다시 흘리면 3~7이 똑같이 나온다. 메일은 실행하지 않고 기록된 결과를 돌려준다. 하네스나 앱 판을 바꿔 돌리면 무엇이 달라지는지가 나온다.

## 8. 만드는 순서 (플랫폼 전체)

이 표가 ARCHITECTURE 10.1의 3~7번과 app-spec 13장의 순서를 하나로 합친 것이다.

| 순서 | 할 일 | 완료 기준 |
|---|---|---|
| 0 | **사용 기록 1차**(10장): 호출 기록, 피드백 도구, 주간 보고 | MCP 호출이 모두 남고 주간 보고가 나온다. 기록은 일찍 시작할수록 쌓인다 |
| 1 | **앱 정의 2단계 + 사람 ID**: 정의 규격과 검증, 지원사업을 데이터로, 이름을 항목(item)으로, 결과에 앱·판, `person`과 `access_link`(토큰 해시). 사람 ID, 정의 규격·검증, 지원사업을 데이터로, 정의의 원본(DB), 결과에 앱·판, 출처 한 장, 이름을 항목으로: 2026-11-24 모두 완료 | 동작이 그대로이고, 비밀 토큰이 DB에 평문으로 없다 |
| 2 | **이벤트 봉투**: `event` 테이블, 타입 등록부, 같이 쓰기, 구독 → 작업 큐. 2026-11-25 완료(2.6) | 지금 일어나는 일이 모두 봉투로 남고, 알림 발송이 봉투를 받아 돈다 |
| 3 | 앱이 읽는 키 기준으로 변경 거르기 (app-spec 3). 판 단위 거르기 2026-11-25 완료, 조각마다 원본 키 적기는 두 번째 앱 전에 | 앱이 읽지 않는 키만 바뀐 버전이 변경 목록에 없다 |
| 4 | **비행 기록기**: `trace`·`record`, 녹화본 색인, 같게 재생. 2026-11-25 1차(3.7) | 수집 실행 하나를 처음부터 다시 돌려 출력이 같다 |
| 5 | 미리 돌려 보기, 비교, 앱 시험, 플랫폼 회귀 시험, 검증 화면 (app-spec 4·5) | 판 두 개의 알림 차이, 플랫폼을 고칠 때 모든 앱의 결과 차이가 나온다 |
| 6 | **개인정보 금고**: 값·동의·허가·암호화·지우기, 대량 판정이 금고 뷰를 읽음 | 동의 밖의 키를 읽는 길이 없다 |
| 7 | **도구 게이트웨이**: 세션·판단·보류 후 확정·승인함, MCP의 B 도구(`check`, `explain`, `get_profile`), 앱을 만드는 조종 도구 (app-spec 6) | B·C 도구가 게이트웨이를 거쳐야만 불린다. RQ6 파일럿 |
| 8 | 사용자 출처 등록, 소유자·구독자·관리자, 예산, 상태 보고 (app-spec 7·8) | 다른 사람이 만든 앱이 내 앱과 섞이지 않고 돈다 |
| 9 | 두 번째 앱 (app-spec 9) | **플랫폼 완성 기준: 두 번째 앱이 플랫폼 코드를 거의 고치지 않고 돈다(RQ7)** |

**왜 이 순서인가**

- **1이 먼저다.** 나머지 모두가 "앱"과 "사람"을 단위로 돈다. 봉투의 `app`·`subject`, 금고의 동의, 게이트웨이의 세션이 모두 이 둘을 가리킨다. 이 둘이 흔들리면 뒤가 다 흔들린다.
- **2가 4보다 먼저다.** 기록기는 봉투를 엮는 것이라 봉투가 있어야 한다.
- **4가 5보다 먼저다.** 미리 돌려 보기와 회귀 시험은 기록기의 "바꿔 재생" 위에 선다.
- **6이 7보다 먼저다.** 게이트웨이의 B 도구는 금고의 허가가 있어야 돈다.
- 금고(6)를 더 앞으로 당기지 않는 이유: 지금 개인정보를 쓰는 곳은 판정 하나뿐이고 사람도 거의 없다. 1번에서 사람 ID와 토큰 해시를 먼저 바로잡으면 가장 큰 위험은 사라진다.

## 10. 에이전트 사용 기록과 개선 고리

### 10.1 왜

이 플랫폼을 주로 쓰는 쪽은 에이전트다. 사람이 쓰는 서비스가 클릭 기록을 보고 화면을 고치듯, **에이전트가 쓴 기록을 보고 도구를 고친다.** 에이전트가 쓰기 편한 정도(에이전트 경험)를 사람의 사용성처럼 다룬다. 쓸수록 도구가 나아지는 고리다.

### 10.2 남기는 것

| 종류 | 남기는 것 | 남기지 않는 것 |
|---|---|---|
| **호출 기록** | 도구와 판, 세션과 순서, 인자 모양(채운 칸·타입·길이), 인자 해시, 상태(`ok`·`error`·`exception`), 오류 문구 앞부분, 결과 크기와 개수, 걸린 시간, 가린 줄 수 | 인자 값, 결과 내용 |
| **허락한 인자** | 도구가 선언한 칸만(예: 검색어). 개인정보를 가리고 100자로 잘라 | 그 밖의 칸 |
| **에이전트 피드백** | `send_feedback(kind, message, tool)`. 종류: 틀림, 부족함, 헷갈림, 느림, 없는 도구, 그 밖 | 개인정보(가림), 1,000자 넘는 부분 |
| **결과 신호** | 승인·거절, 사람이 고친 것 (게이트웨이가 생긴 뒤) | |

### 10.3 기록에서 알아내는 것과 고치는 법

| 보이는 것 | 뜻 | 고치는 법 |
|---|---|---|
| 특정 도구의 오류가 많다 | 설명이나 입력 모양이 헷갈린다 | 도구 설명·스키마 고치기 |
| 오류 뒤 같은 도구를 다시 부른다 | 기본값이 맞지 않거나 결과가 부족하다 | 기본값, 한도 조정 |
| 늘 이어서 불리는 도구 쌍이 있다 | 하나의 일을 여러 번에 나눠 한다 | 합친 도구 만들기 |
| 검색했는데 결과가 없다 | 모으지 않는 출처를 찾는다 | **새 출처 후보** (출처 카탈로그의 수요 신호) |
| 안 쓰이는 도구 | 필요 없거나 존재를 모른다 | 정리하거나 설명 고치기 |
| 결과가 늘 크다 | 한도가 좁거나 넓다 | 한도·나눠 받기 조정 |
| 가린 줄이 많다 | 위험한 출처, 또는 오탐 | 하네스 조정 |

### 10.4 고리

1. **기록**: 모든 도구 호출이 지나는 한 길에서 남긴다. 1차는 등록부(`tooling.Registry`), 나중에는 게이트웨이.
2. **주간 보고**: `scripts/usage_report.py`. 도구별 호출·오류율·재시도·결과 없음·걸린 시간, 이어 부른 도구 쌍, 안 쓰인 도구, 결과 없는 검색어, 새 피드백.
3. **고침**: 도구 설명·입력·기본값을 고치고 도구 판(`Tool.version`)을 올린다.
4. **판별 비교**: 같은 보고서를 도구 판별로 나눠, 고친 게 실제로 나아졌는지 본다.
5. **시험으로 남기기 (나중)**: 실제 세션의 흐름을 시험 시나리오로 저장해, 도구를 고칠 때마다 우리 에이전트로 다시 돌린다.

### 10.5 조심할 것

- **값 대신 모양과 해시.** 인자 해시는 같은 호출의 반복을 찾는 데만 쓰고 밖으로 내보내지 않는다. 값이 몇 개 안 되는 칸은 해시로도 맞혀 볼 수 있기 때문이다.
- **피드백 글은 신뢰할 수 없는 입력(A)이다.** 자동으로 적용하지 않는다. 보고서에 보일 때 지시로 보이는 줄은 가리고, 사람이 읽고 상태를 바꾼다(`new` → `reviewed` → `acted`·`dismissed`).
- **기록이 실패해도 도구 호출은 그대로 돈다.** 기록은 표준 오류로만 경고한다(stdio MCP는 표준 출력이 통신 길이다).
- **다른 사람의 에이전트가 붙으면** 사용 기록을 모은다는 사실을 서버 안내문에 적고, 보관 기한(기본 180일)이 지나면 지운다(`usage_report.py --purge-days`).

### 10.6 설계상 자리

새 부품이 아니라 비행 기록기(4번)와 게이트웨이(7번) 위에 얹는 고리다. 그 둘은 순서상 뒤에 있으므로, **기록만 먼저(0번) 작게 시작한다.** 기록기가 생기면 `tool_call`은 `record(kind=tool_call)`로 옮기고, 게이트웨이가 생기면 게이트웨이의 판단과 세션 표시가 더해진다. 테이블 모양은 그때 옮기기 쉽게 맞춰 둔다.
