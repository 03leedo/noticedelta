# 서비스 구상 메모 (보류)

| 항목 | 내용 |
|---|---|
| 상태 | **보류.** 2026-11-17에 플랫폼을 먼저 완성하기로 했다(ARCHITECTURE.md 10장). 여기 적힌 것은 결정이 아니라 그때까지 생각해 둔 것이다. |
| 다시 볼 때 | 플랫폼 공통 기능이 갖춰진 뒤, 그 위에 서비스를 얹었을 때의 효과를 보여 줄 차례에 |

## 정해 둔 원칙

- **플랫폼이 주 프로젝트다.** 서비스는 플랫폼 위에 얹은 사례다.
- **변경 영향 엔진은 플랫폼 기능 중 하나다.** 서비스가 엔진을 주로 쓰는 모양이 되면 안 된다. 서비스는 그 자체로 쓸 이유가 있어야 하고, 플랫폼 기능은 뒤에서 받친다.
- 서비스의 차별점은 새 기능보다 **같은 일을 얼마나 잘하느냐(수준)**에서 찾는다.
- 베타 사용자는 개인으로 모은다. 기관(창업지원단, 보육센터, 컨설턴트)은 나중이고, 막지 않게만 만든다.

## 왜 지금 서비스에 차별점이 안 보이는가

- 화면은 "조건을 넣으면 맞는 지원사업이 나온다"이다. 기업마당 맞춤 알림이나 정책 추천 서비스와 겉모습이 같다.
- "정정 영향 알림"은 드물게만 일어난다. 한 달 동안 사업 약 2,300개 중 실제 정정은 49건(약 2%)이었다. 대부분의 사용자는 겪지 못한다.

## 사용자가 실제로 하는 일과 빈 곳

| 단계 | 어려움 | 기존 서비스 |
|---|---|---|
| 1. 찾기 | 공고가 많고 흩어져 있다 | 여기에 몰려 있다 |
| 2. 고르기 | 받을 수 있는지, 해 볼 만한지 모른다 | 거의 없다 |
| 3. 준비 | 서류, 일정, 신청서 양식 | 없다 |
| 4. 신청 직전 | 빠뜨린 것, 그사이 바뀐 것 | 없다 |
| 5. 그 뒤 | 결과, 다음 회차, 내년 공고 | 없다 |

## 후보: 신청 준비함을 중심으로

"고른 사업을 신청까지 끝내게 해 주는 작업 공간"(ARCHITECTURE.md 6.1). 플랫폼 기능은 전부 뒤에서 일한다.

| 서비스에서 보이는 것 | 받치는 플랫폼 기능 |
|---|---|
| 제출 서류 체크리스트, 양식 안내 | 문서 파싱 |
| 내 회사 정보와 서류를 올려도 안전함, 여러 신청에 다시 씀 | 개인정보 금고, 하네스 |
| 초안 작성, 기관 문의 메일 | LLM 게이트웨이, 도구 게이트웨이(승인) |
| 공고가 정정되면 체크리스트와 일정이 알아서 바뀜 | 변경 영향 엔진 |

가볍게 먼저 넣을 수 있는 것: 관심 사업 담기, 서류 체크리스트(추출 필드에 "제출 서류"가 있다), 마감까지 남은 날.

## 수준을 숫자로 보이는 방법 (후보)

- **겉 정보만 본 매칭 대 첨부까지 읽은 판정**: API의 겉 정보(지역, 대상 태그)만으로 "해당"이라고 한 사업 중, 첨부의 조건을 읽으면 실제로는 탈락하는 비율.
- 품질 기준: "해당" 중 실제로 신청 가능한 비율, "확인 필요" 비율, 원문 근거가 붙은 판정의 비율, 정정이 판정에 반영되기까지 걸린 시간.
- 전부 추출 정확도에 달려 있다. LLM 추출 실측(작업 목록 5번) 결과를 보고 판단한다.

## 그 밖에 나온 생각

- 알림 채널(이메일), 급한 것은 즉시·나머지는 묶음.
- 판정마다 "맞아요/틀렸어요": 베타 지표(판정 동의율)이자 평가 라벨.
- "확인 필요" 줄이기: 프로필을 다 채우게 하지 않고, 가장 많은 공고의 판정을 가르는 질문부터 묻는다.
- 자격이 생기거나 사라지는 날 알림(계산은 이미 있다).
- 공고에 묻고 답하기(원문 근거와 인용 검증).
- 기관용: 한 사람이 여러 프로필을 본다. 프로필 위에 묶음 하나를 얹으면 된다(판정·알림·구독은 이미 프로필 단위).
- 출처 확대: 지자체, 소상공인 정책자금, R&D 과제.

## 이미 만들어 둔 서비스 쪽 것 (그대로 둔다)

판정 화면, 알림함, 공고 상세·변경 이력, 알림 근거 화면, ICS 캘린더, 동의 화면과 내 정보 지우기, VM 배포 구성(`deploy/`). 플랫폼 기능을 보여 주는 예시 앱으로 쓴다.
