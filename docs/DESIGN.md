## 0. 한 줄 요약

예비·초기 창업자가 프로필을 등록하면, 시스템이 맞는 정부 지원사업을 찾아 **자격을 코드로 판정**하고 공고를 계속 추적한다. 정정공고나 첨부 HWP가 바뀌면 **바뀐 문단에 걸린 필드만 다시 추출**하고, 판정이 실제로 달라진 사용자에게만 근거 조항과 함께 알린다.

이 프로젝트는 두 가지를 함께 만든다.

1. **기간 한정 실서비스**: 3~4주 동안 실제 사용자(창업동아리 등)에게 운영한다.
2. **오래 남는 기술 산출물**: 오픈소스 엔진, 공개 평가 데이터셋, 재현 가능한 실험 결과. 서버를 내려도 남는다.

## 1. 목표와 비목표

### 목표
- G1. 공고 변경이 생겼을 때 **LLM 호출 수가 사용자 수와 무관**한 변경 영향 엔진을 만든다.
- G2. 자격 판정은 **결정적 코드**로 하고, 모든 판정에 원문 근거 위치를 붙인다.
- G3. PostgreSQL 작업 테이블과 단일 워커로 **재시도·멱등성·순서 보장·관측**을 갖춘 파이프라인을 만든다.
- G4. (동결 뒤 실험) **안 쓸 때 0으로 줄어드는** 배포(KEDA)로 운영비를 잰다.
- G5. LLM 응답 녹화·재생으로 **누가 돌려도 같은 결과가 나오는** 실험과 서버 없는 데모를 만든다.
- G6. 외부에서 온 첨부 파일과 공고 텍스트를 **격리된 환경**에서 처리한다(이전 보고서의 격리·권한 원칙 적용).
- G7. 연구 질문 RQ1·RQ2의 측정 결과를 사람 라벨 기준으로 남긴다(3장).

### 비목표
- 신청서 자동 제출 (준비 보드·사업계획서 초안은 플랫폼 2단계의 신청 준비함에서 다룬다. ARCHITECTURE.md 6.1)
- 모든 지자체·기관 공고 커버 (MVP는 K-Startup + 기업마당)
- 모바일 앱, 카카오 알림톡 (초기 범위 밖)
- 법률·세무 자문. 판정은 "참고용"이며 최종 확인은 공고 원문이다.
- 장기 상시 운영. 12월은 비공개 베타(5~10명)와 과거 정정 재생 데모, 실운영은 2027년 2~3월 지원사업 시즌에 기간을 정해 한다.
- 회원가입·로그인(1단계는 추측할 수 없는 개인 링크와 ICS), 민감정보(장애 여부 등) 수집.

## 2. 배경과 문제

### 2.1 사용자 문제
- 지원사업 공고는 원공고 뒤에 **정정공고**(마감 연장, 자격 조건 변경, 예산 소진, 서류 추가)가 붙는 경우가 있다. 정정 내용은 본문이나 첨부 HWP 안에 있어 놓치기 쉽다.
- 사용자가 알고 싶은 건 "새 글이 올라왔다"가 아니라 **"그래서 나는 아직 신청할 수 있나, 마감은 언제로 바뀌었나"**다.

### 2.2 기존 서비스와의 차이 (2026-10-04 조사, 출처는 17장)

| 구분 | 대표 사례 | 하는 일 | 이 프로젝트와의 차이 |
|---|---|---|---|
| 지원사업 서비스 | 지원금AI(govmatch.kr), kfund.ai, 지원매치, gongo-radar | 조건 매칭, 키워드·신규 공고 알림, 마감 임박 알림, 상담 챗봇 | 정정공고로 인한 **자격·마감·금액 변경을 재판정해 알리는** 기능은 확인되지 않음 |
| 범용 "답 변경" 모니터 | Parallel Monitor API(snapshot), ChatGPT 예약 작업 | 질문(작업)마다 **주기적으로 다시 실행**하고 이전 결과와 비교 | 질문 수만큼 LLM 호출. 이 프로젝트는 **문서 변경 이벤트에서 영향받는 필드·사용자만** 골라 처리 |
| 개념 선례 | Pathway 데모(2023) | 문서 변경 시 영향 질문 판정, LLM으로 답 비교 | 규모 처리·비용 측정 없음 |
| 검색 엔진 기능 | OpenSearch percolator | 저장된 질의에 새 문서를 역매칭 | 벡터(kNN) 질의는 percolator 미지원 (이슈 #3543) |

**포지셔닝**: "질문이 바뀌면 알려 준다"는 개념은 새롭지 않다. 이 프로젝트의 기여는 **같은 일을 사용자 수와 무관한 비용으로, 근거와 함께, 재현 가능하게** 하는 엔진과 그 측정이다.

## 3. 연구 질문

| ID | 질문 | 주요 지표 |
|---|---|---|
| RQ1 | 변경 영향 엔진은 전체 재추출(B2)과 diff 기반 LLM(B3)에 비해, **사람 라벨 기준 재현율이 같을 때** 토큰과 가짜 알림을 얼마나 줄이는가? | 이벤트당 입력·출력 토큰, 사람 라벨 기준 필드 변경 재현율·정밀도(95% CI), 문구만 바뀐 정정·변경 없는 재수집에서의 가짜 알림률, B2 잡음 바닥(같은 버전 재추출 시 값 불일치율), 놓침 원인(인용 조각 대 정답 위치) |
| RQ2 | 조각 맞추기 방식(해시만 / 해시+유사도 / 원문 diff)에 따라 놓침률과 비용은 어떻게 달라지는가? | 합성 변형 세트와 실제 정정에서 놓친 변경, 잘못 잡은 변경, 처리 시간 |
| RQ6 | (2단계 파일럿) 도구 게이트웨이는 매 행동 승인·샌드박스 단독보다 승인 횟수와 피해 범위를 얼마나 줄이는가? | ARCHITECTURE.md 8장 |

- **B1(질문별 재실행) 대비 호출 수 감소는 구조상 당연하므로 주장하지 않는다.** "LLM 호출이 사용자 수와 무관함"은 설계 속성으로, 사용자 1명 → 10만 명일 때 호출 수가 평평한 확장 그래프로만 보인다.
- v0.4의 RQ3(필드 비교 대 LLM 답 비교)은 RQ1의 가짜 알림 지표로, RQ5(인용을 의존 관계로 쓰기)는 RQ1의 놓침 원인 분석으로 합쳤다. RQ4(KEDA)는 연구 질문이 아니라 운영 측정(9.4)으로 내렸고, RQ7(팩 추가 비용)은 팩 하나로는 사례 1건이라 뺐다.

## 4. 사용자와 시나리오

### 4.1 MVP 사용자
- **예비·초기 창업자** (K-Startup 공고 중심). 첫 사용자 채널은 학교 창업지원단, 창업동아리, 창업 커뮤니티.

### 4.2 대표 시나리오
1. 사용자가 프로필을 등록한다(5분 이내): 예비창업자 여부, 대표자 나이, 지역, 업종, 업력, 사업자 유형, 매출, 상시근로자 수, 우대 대상(여성·재창업 등).
2. 시스템이 열린 공고 전체에 대해 자격을 판정해 **해당 / 확인 필요 / 비해당**으로 보여준다. 판정마다 근거 조항이 붙는다.
3. 사용자가 관심 공고를 고르면 마감일·금액·자격·필요 서류가 자동으로 추적된다. 캘린더(ICS)에 마감일이 들어간다.
4. 2주 뒤 정정공고가 올라온다. 첨부 HWP 안의 표에서 업력 조건이 7년에서 5년으로 바뀌었다.
5. 시스템은 바뀐 표 칸에 걸린 "자격 규칙" 필드만 다시 추출하고, 이 공고를 추적하던 사용자만 재판정한다.
6. 업력 6년인 사용자에게만 알림이 간다: "정정공고로 업력 조건이 7년 → 5년으로 바뀌어 자격에서 빠졌습니다 (첨부 3쪽 표 2)". 변경 이력 화면에서 이전/이후 차이가 색으로 표시된다.

## 5. 시스템 개요

```text
[출처] K-Startup API · 기업마당 API · 상세 페이지 첨부(HWP/HWPX/PDF)
   │
   ▼
① 수집 (fetch)        목록·첨부를 가져와 해시 비교, 바뀐 것만 다음 단계로
   ▼
② 저장                원문은 객체 스토리지(내용 해시 키), 메타데이터는 PostgreSQL
   ▼
③ 격리 파싱 (parse)   네트워크 없는 컨테이너에서 문단·표 칸 단위 조각으로 변환
   ▼
④ 변경 감지 (diff)    이전 버전 조각과 맞춰 추가·삭제·수정 조각 계산
   ▼
⑤ 추출 (extract)      LLM으로 필드(마감일·금액·자격 규칙·서류) 추출 + 출처 조각 기록
   ▼
⑥ 영향·판정 (impact)  바뀐 조각 → 영향 필드 → 진짜 변경 판정 → 영향 사용자 재판정(코드)
   ▼
⑦ 알림 (notify)       아웃박스에 기록된 알림만 발송, 캘린더·체크리스트 갱신
   ▼
[웹] 프로필 · 내 공고 · 공고 상세 · 변경 이력 · 알림함 · 운영 대시보드
```

- 각 단계는 **PostgreSQL 작업 테이블의 작업 종류**이고, 워커 프로세스 하나가 모든 종류를 처리한다(8장). 단계마다 따로 재시도한다.
- 모든 LLM 호출은 **LLM 게이트웨이**(10장)를 거친다. 녹화·재생, 비용 집계, 호출 한도 관리를 여기서 한다.

## 6. 데이터 모델

핵심 테이블만 적는다. 이름은 구현 때 바뀔 수 있다.

| 테이블 | 주요 컬럼 | 설명 |
|---|---|---|
| `source` | id, name, base_url, rate_limit | 공고 출처 |
| `notice` | id, source_id, external_id, title, org, status(open/closed), current_version_id | 공고 |
| `notice_version` | id, notice_id, version_no, kind(original/correction), fetched_at, content_hash | 공고 버전. 원공고와 정정마다 하나 |
| `attachment` | id, notice_version_id, filename, mime, blob_key, parse_status | 첨부. 원문은 `blob_key`(sha256)로 객체 스토리지에 |
| `segment` | id, notice_version_id, lineage_id, kind(paragraph/heading/table_cell), text, text_hash, locator(json), embedding | 조각. `lineage_id`는 버전이 바뀌어도 "같은 조각"이면 유지 |
| `field_value` | id, notice_id, version_id, name, value(json), value_type, source_lineage_ids[], confidence, extractor | 필드 값. 버전별 이력 보관 |
| `eligibility_rule` | id, notice_id, version_id, group_id, attribute, op, value, source_lineage_id, confidence | 자격 규칙(7.6절 형식) |
| `profile` | user_id, attributes(json, 타입 고정) | 사용자 프로필 |
| `subscription` | id, user_id, notice_id, fields[] | 추적 구독 |
| `free_question` | id, user_id, notice_id, text, embedding, last_answer(json), answered_version_id | 자유 질문 (선택 기능) |
| `judgment` | id, user_id, notice_id, version_id, result(eligible/ineligible/unknown), reasons(json) | 판정 결과와 근거 |
| `change_event` | id, program_id, from_version_id, to_version_id(사업 버전), changed_lineages(json: added·removed·modified·unknown), matcher_version, created_at | 변경 이벤트. 재생(10장)의 기준 로그. 사업 버전마다 조각(lineage 포함)과 함께 남겨 매칭 없이 같은 변경을 다시 만든다 |
| `outbox_alert` | id, idempotency_key(unique), user_id, notice_id, payload(json), status, created_at, sent_at | 알림 아웃박스 |
| `job_ledger` | stage, job_key(unique), status, attempts, updated_at | 단계별 멱등 처리 기록 |

색인 포인트:
- `field_source_index(lineage_id → field)`: 바뀐 조각에서 영향 필드를 바로 찾는다.
- `subscription(notice_id, field)`: 영향 필드에서 구독자를 바로 찾는다.
- `segment.embedding`, `free_question.embedding`: pgvector.

### 6.1 v0.5에서 바뀌는 점 (사업 모델 PR에서 구현)

외부 평가 검토에서 가장 큰 구멍은 **사업 단위가 없다**는 것이었다. 기업마당은 정정할 때마다 새 번호로 다시 올리고 원공고를 닫는다. 구독·판정·알림이 포털별 공고 번호에 걸려 있으면, 정정이 나오는 그 순간 구독자에게 알림이 가지 않는다.

| 테이블 | 역할 |
|---|---|
| `program` | 사업. 구독·필드·판정·알림의 주인 |
| `posting` | 포털 게시물(출처, 외부 ID). 사업 1 : 게시물 N |
| `snapshot` | 수집할 때마다 받은 API 원본(상시 수집 파일을 그대로 적재) |
| `program_version` | 엔진의 입력이 되는 의미 있는 내용 버전. 버전 트리거는 합성 해시(7.1) |
| `program_link` | 게시물 → 사업 연결(방법, 점수, 결정자, 시각). 점수가 낮으면 자동으로 합치지 않고 운영자 확인. 잘못 합치는 것이 놓치는 것보다 위험하다 |
| `attachment_lineage` | 버전 사이의 같은 첨부(정정 표시를 뺀 파일 이름 + 역할 + 순번). 표 짝짓기 키에 쓴다 |
| `job` | 작업 큐(8장). `job_ledger`를 대신한다 |

- `subscription`, `judgment`, `field_value`, `outbox_alert`의 키를 `notice_id`에서 `program_id`로 바꾼다. `judgment`는 덮어쓰지 않고 쌓는다.
- `field_value`에 상태(verified / needs_review / stale)와 추출 프롬프트 버전, LLM 호출 키를 둔다.
- 포털 간 중복(K-Startup과 기업마당)은 1단계에서 연결만 하고 내용은 합치지 않는다. 첨부가 있는 기업마당 게시물을 사업의 주 게시물로 둔다.
- 스키마는 마이그레이션 도구(Alembic)로만 바꾼다.

## 7. 파이프라인 단계별 설계

### 7.1 수집
- **공식 API만 쓰고 웹 스크래핑은 하지 않는다**(확인 결과: `docs/research/terms.md`).
  - 본문: K-Startup 사업공고 API(data.go.kr 15125364). 첨부 URL은 주지 않는다.
  - 첨부: 기업마당 지원사업정보 API(data.go.kr 15157820)의 첨부 필드. 공공누리 3유형(출처표시+변경금지)이라 원문 인용은 고치지 않고, 첨부는 재배포하지 않는다.
- **포털별 버전 추적이 다르다**(확인 결과: `docs/research/corrections.md`, 표본 28건).
  - K-Startup은 같은 공고 번호를 덮어쓰는 경우가 많다 → 같은 `external_id`를 주기적으로 다시 받아 내용 해시를 비교한다.
  - 기업마당은 수정할 때마다 새 번호로 다시 올리고 원공고를 "조기마감 사유: 수정공고 업로드"로 닫는다 → 제목 정규화·공고번호·조기마감 사유로 **원공고와 짝짓는 단계**가 필요하다.
  - 두 포털에 같은 공고가 함께 올라오므로 사업 단위로 중복을 합친다.
  - 제목의 "수정·정정·연장"은 "바뀌었을 수 있다"는 신호로만 쓰고, 무엇이 바뀌었는지는 비교로 확정한다.
- **적응형 주기**: 마감 임박 또는 구독자 많은 공고는 1시간, 일반 공고는 하루 몇 번, 마감 공고는 중단.
- **바뀐 것만 처리**: 목록 항목과 첨부의 해시가 같으면 다음 단계로 넘기지 않는다.
- **상시 수집(2026-10-23부터)**: 두 출처의 열린 공고 전체를 6시간마다 파일로 스냅샷한다(`snapshot.py`, 집 PC 예약 작업). DB·Docker 없이 돌고, 나중에 사업 모델로 다시 넣는다. 첫 실행: K-Startup 231건, 기업마당 1,460건, 첨부 3,048개.
- **기업마당 API는 열린 공고만 준다**(2026-10-23 확인: 마감이 지난 항목 0건). 닫힌 원공고를 API로 백필할 수 없으므로 정정 쌍은 상시 수집으로만 얻는다.
- **버전 트리거(사업 모델 PR에서)**: API 응답 해시가 아니라 "정규화 본문 + 첨부 내용 해시 목록"의 합성 해시가 바뀔 때만 새 버전을 만든다. 같은 URL의 첨부 내용만 바뀌는 경우를 놓치지 않기 위해서다. `version_no`는 도착 순서가 아니라 출처 시각 순이다.
- **출처별 속도 제한과 서킷 브레이커**: 기관 사이트에 부담을 주지 않고, 장애 시 잠시 멈췄다가 재개한다.

### 7.2 저장
- 원문은 S3 호환 객체 스토리지(로컬 SeaweedFS, 클라우드 Cloudflare R2)에 **내용 해시를 키로** 저장한다. 같은 파일은 한 번만 저장된다.
- 메타데이터·조각·필드·판정은 PostgreSQL, 임베딩은 pgvector.

### 7.3 격리 파싱
- HWP/HWPX/PDF를 오픈소스 파서로 문단·표 칸 단위 조각으로 바꾼다. 기본은 kordoc, HWP·HWPX에서 kordoc이 실패하면 hwp-hwpx-parser로 한 번 더 시도한다(`docs/research/parsers.md`). 조각마다 `locator`(첨부, 쪽, 표 번호, 행·열, 행 키, 열 머리글)를 기록한다.
- 표의 병합 칸이 덮는 자리는 조각을 만들지 않는다. 첫 열이 세로로 병합된 분류 칸이면 둘째 열까지 행 키로 써서 행이 겹치지 않게 한다.
- 파서 출력(계약 JSON)은 원문 저장소에 내용 해시 키로 두고, 조각은 언제든 그 JSON에서 다시 만든다.
- 파서는 **네트워크 차단, 읽기 전용 파일시스템, CPU·메모리·시간 제한, 비루트 사용자** 컨테이너에서 돈다(11장). 입력은 객체 스토리지 키, 출력은 JSON뿐이다.
- 실패 분류: 일시 장애(재시도), 멈춤(인증키·설정 오류, 운영 알림), 문서 문제(`needs_review`), 미지원 형식(`unsupported`), 사라짐(404)으로 나눈다. **Docker가 꺼졌거나 파서 이미지가 없는 인프라 장애는 `needs_review`로 굳히지 않는다**(`ParserUnavailable`, 첨부는 pending 유지).
- 버전 완전성: 새 버전의 첨부가 모두 끝 상태일 때만 조각 비교를 돌린다. 파싱하지 못한 첨부의 옛 조각은 "삭제"가 아니라 "알 수 없음"으로 둔다(가짜 "조건 삭제" 알림 방지, 사업 모델 PR에서).
- 파서 버전을 올리면 조각 해시가 전부 바뀐다. 이미지 digest와 파서 버전을 기록하고, 올릴 때는 이전 버전도 새 파서로 다시 파싱해 비교한다.
- 실패 처리: 같은 공고의 PDF판이 있으면 그것으로 재시도 → 그래도 실패하면 `parse_status=needs_review`로 운영자 검토 목록에 올린다. 조용히 넘기지 않는다. 파싱은 됐어도 글자가 50자 미만이거나 한글 비율이 30% 미만이면(스캔본, 글꼴 대응표가 깨진 PDF) 역시 `needs_review`다. ZIP 묶음 등 파싱하지 않는 형식은 `unsupported`로 남긴다.

### 7.4 변경 감지 (조각 맞추기)
이전 버전과 새 버전의 조각을 짝지어 `lineage_id`를 이어 준다.

1. **해시 일치**: 텍스트 해시가 같으면 같은 조각.
2. **순서 정렬 + 유사도**: 남은 조각은 문서 순서 기준 정렬(diff 알고리즘)과 문자 n-gram 또는 임베딩 유사도로 "수정된 조각"을 짝짓는다. 임계값 아래면 추가·삭제로 본다.
3. **표**: 표 머리글 서명과 행 키(첫 열)로 표와 행을 먼저 맞추고, 칸 단위로 비교한다.
4. (실험 변형) **LLM 보조**: 애매한 짝만 LLM에 확인시킨다. RQ2에서 비용·정확도를 비교한다.

출력은 `change_event`(바뀐 lineage 목록)다.

### 7.5 추출
- LLM이 구조화 출력(JSON 스키마)으로 필드를 뽑는다: `deadline`, `amount`, `eligibility_rules`, `required_documents`, `contact`.
- 모든 값에 **출처 조각 ID**를 함께 출력하게 한다.
- **인용 검증**: 추출한 날짜·금액·숫자가 인용한 조각 텍스트 안에 실제로 있는지 코드로 확인한다. 없으면 신뢰도를 낮추고 "확인 필요"로 둔다.
- 첫 추출은 공고 전체, 이후 정정에서는 7.6의 **부분 재추출**만 한다.

### 7.6 자격 규칙 형식과 판정기

**속성 사전(고정 어휘)**: `is_pre_founder`, `business_age_months`, `ceo_age`, `region_sido`, `industry_ksic`, `business_type(individual/corporation)`, `revenue_krw`, `employees`, `is_women_owned`, `is_restart` 등. 사전에 없는 조건은 억지로 매핑하지 않는다.

**규칙 형식**

```json
{
  "group": "all_of",
  "rules": [
    { "attribute": "business_age_months", "op": "<=", "value": 84, "source": "lineage:42" },
    { "attribute": "region_sido", "op": "not_in", "value": ["서울", "경기", "인천"], "source": "lineage:43" }
  ],
  "manual": [
    { "text": "타 정부지원사업 중복 수혜 불가", "source": "lineage:51" }
  ]
}
```

- 연산자: `== != < <= > >= in not_in between`, 그룹: `all_of / any_of`.
- 사전에 없는 조건은 `manual`(텍스트 그대로)로 둔다.

**판정 규칙**
- 결과는 **해당 / 비해당 / 확인 필요** 세 가지다.
- 규칙 하나라도 거짓이면 비해당. 프로필에 값이 없거나, 규칙 신뢰도가 낮거나, `manual` 조건이 있으면 해당이 아니라 **확인 필요**로 둔다. 잘못된 비해당으로 기회를 놓치게 하지 않는 쪽을 우선한다.
- 판정 근거(`reasons`)에 규칙 ID와 원문 위치를 넣는다.
- **대량 판정**: 새 공고가 들어오면 규칙을 SQL 조건으로 바꿔 `profile` 테이블에 한 번에 질의한다. 사용자 수가 늘어도 LLM 호출은 늘지 않는다.

### 7.7 변경 영향 엔진 (핵심)

```text
change_event(바뀐 lineage 목록)
  ① 영향 필드 = field_source_index에서 바뀐·삭제된 lineage에 걸린 필드
     + 새로 추가된 조각은 가벼운 검사기(날짜·금액·자격 키워드 정규식, 필드 설명과의 임베딩 유사도)로
       관련 필드 후보를 고름
  ② 부분 재추출 = 영향 필드만 LLM으로 다시 추출 (바뀐 조각 + 주변 문맥만 입력)
  ③ 진짜 변경 판정 = 타입별 비교
       날짜: KST로 정규화해 비교 / 금액: 원 단위 숫자로 비교 / 규칙: 정규화한 집합으로 비교
       → 값이 같으면 "문구만 바뀜"으로 보고 종료 (알림 없음)
  ④ 영향 사용자 = subscription(notice_id, 바뀐 필드) 조회
       자격 규칙이 바뀌었다면 이 공고에 판정 기록이 있는 사용자 전체
  ⑤ 재판정 = 7.6 판정기(코드)
  ⑥ 판정 결과나 추적 필드가 실제로 달라진 사용자만 outbox_alert에 기록
```

**자유 질문(선택 기능)**: 질문은 공고 단위로 묶여 있어 후보가 작다. 바뀐 조각 임베딩과 그 공고의 질문 임베딩을 비교해 가까운 질문만 다시 답하고, 답을 구조화해 비교한다.

**엔진이 조용히 틀리지 않게 (v0.5)**
- 지워진 조각도 옛 글로 키워드 검사한다. 표 칸은 열 머리글·행 키까지 함께 본다.
- 근거 조각이 바뀌었는데 다시 찾지 못한 필드는 옛 값을 믿지 않고 `stale`로 낮춘다.
- 자격 규칙이 바뀌면 판정 기록이 없는 사용자까지 다시 판정한다(조건 완화로 새로 해당하게 된 사람).
- 규칙이 하나도 없는 자격 그룹은 "해당"이 아니라 "확인 필요"다. 규칙 근거는 단위(세·년·명)와 방향(이하·이상)까지 확인한다.

**안전망**: 변경 이벤트마다 그 사업만 B2(전체 재추출)를 **다른 프롬프트 버전으로** 그림자 실행하고, 주 1회 열린 공고의 10%를 표본으로 다시 수집·재추출한다. 이 차이는 "B2와의 불일치"로만 보고하고, **놓침은 사람 라벨로만 센다**(같은 계열 LLM끼리의 비교는 정답이 아니다).

### 7.8 알림
- 알림 상태: `pending → held | ready → sending → sent`, 그리고 `superseded`(보내기 전에 같은 필드가 다시 바뀜), `discarded`, `corrected`(틀린 알림을 바로잡음). `idempotency_key = (user_id, program_id, field, to_version_no)`라서 같은 알림은 두 번 가지 않는다. 이메일은 최소 한 번 전달이며 중복은 발송사 멱등 키로 줄인다.
- **붙잡기(held)**: 신뢰도가 낮거나 인용 검증에 실패한 값, 근거 첨부가 `needs_review`인 경우, 영향이 큰 전환(비해당 전환·마감 단축·금액 감소)이 N명 이상에게 가는 경우, 변경 하나가 알림을 M건 넘게 만드는 경우. 해제는 운영자 확인 또는 그림자 B2 일치로 한다.
- 채널: **ICS 구독 URL이 기본**(정정 시 캘린더 이벤트의 제목·설명이 바뀜), 이메일은 원하는 사람만. 웹 푸시·디스코드·슬랙 웹훅은 1단계 밖이다.
- 알림 본문은 템플릿과 타입 값(날짜·금액·판정)만 쓴다. 원문 인용은 이스케이프하고 길이를 제한하며, 링크는 자체 상세 화면과 출처 포털 도메인만 쓴다. 추출한 문의처는 알림에 넣지 않는다. **LLM이 만드는 한 줄 설명은 1단계에서 뺀다.**

## 8. 신뢰성 설계

| 주제 | 설계 |
|---|---|
| 작업 큐 | **PostgreSQL 작업 테이블**(`job`): `SELECT … FOR UPDATE SKIP LOCKED`로 꺼내고, 단계 결과 기록과 다음 작업 등록을 한 트랜잭션으로 묶는다. 워커 프로세스는 하나 |
| 멱등성 | 작업마다 `dedupe_key`(UNIQUE). 파싱은 `(첨부 sha256, 파서 이미지 digest, 계약 버전)`, 비교는 `(program, from_ver, to_ver, matcher 버전)`처럼 내용 주소 키 |
| 알림 중복 방지 | 아웃박스 패턴: 판정 결과와 알림 기록을 같은 DB 트랜잭션으로 쓰고, 발송은 별도 작업 |
| 순서 보장 | 사업 하나의 작업은 직렬(`concurrency_key = program_id`). `version_no`가 클 때만 현재 버전을 바꾼다 |
| 워커 장애 | 작업 임대(`lease_until`)가 지나면 다른 실행이 다시 가져간다 |
| 반복 실패 | `error_class`가 일시 장애일 때만 지수 백오프로 재시도, 횟수를 넘기면 `dead`로 보내고 운영 알림 |
| 외부 장애 | 출처별 서킷 브레이커(어떤 실패든 결과를 기록해 시험 칸이 풀린다), LLM 한도 초과 시 우선순위(마감 임박·구독자 많은 사업 먼저) |
| 놓침 대비 | 이벤트별 그림자 B2와 주간 10% 표본(7.7) |

## 9. 인프라와 배포

### 9.1 로컬 (개발·데모)
- `docker compose up` 하나로 PostgreSQL(pgvector), S3 호환 저장소(SeaweedFS), API, 워커, 웹이 뜬다. 상시 수집은 compose와 따로 집 PC 예약 작업으로 돈다.
- **데모 모드**: 녹화된 LLM 응답과 과거 정정 이벤트로 실제 흐름을 서버 없이 재현한다(10장).

### 9.2 클라우드 (기간 한정 운영·실험)
- **k3s 클러스터**: 작은 상시 노드 1대(API, DB, 워커, 스케줄러) + 필요할 때만 붙이는 스팟/저가 노드(백필·부하 시험).
- **KEDA로 0까지 자동 확장 (동결 뒤 실험)**: 워커를 PG 작업 테이블의 대기 작업 수(KEDA PostgreSQL scaler) 기준으로 0~N개 사이에서 늘리고 줄인다.
- **Terraform**: VM, 네트워크, DNS, 객체 스토리지 버킷을 코드로 관리한다. `terraform destroy` 한 번으로 내리고, 다시 올릴 수 있다.
- **클라우드 후보**: 무료·저가 구간이 있는 곳(예: Oracle Cloud Always Free, 저가 VPS) + Cloudflare R2. 조건은 1주차에 확인한다.

### 9.3 메시징 단계
- PostgreSQL 작업 테이블 하나로 간다(8장). 데이터 양(하루 정정 몇 건, 새 버전 수십 건)에서 Redis Streams를 두면 DB 커밋과 큐 등록이 원자적이지 않아 오히려 신뢰성이 떨어진다. Redis와 Redpanda 비교는 뺐다.

### 9.4 관측
- OpenTelemetry로 단계 간 추적 ID를 메시지에 실어 보낸다. 지표는 Prometheus, 화면은 Grafana.
- 핵심 지표: 단계별 대기 작업 수와 처리 시간, 정정 반영→알림 지연(p50/p99), LLM 호출·토큰·비용, 파싱 실패율, 워커 수(자동 확장 동작 확인).

### 9.5 규모를 만드는 방법 (정직한 설명)
평소 공고 양은 많지 않다. 그래서 규모는 아래 두 가지로 만든다.
- **과거 공고 백필**: 과거 공고와 정정 이력을 한꺼번에 처리한다.
- **이벤트 재생 부하 시험**: 가상 프로필·구독 10만 건 + 과거 정정 이벤트를 N배속으로 재생한다. 처리량, 지연 p99, 자동 확장 동작, 비용을 잰다.

## 10. 녹화·재생

### 10.1 LLM 게이트웨이
모든 LLM 호출은 게이트웨이 한 곳을 거친다.
- 키: `hash(model, prompt_template_version, input, output_schema)`
- 모드: `live`(그냥 호출) / `record`(호출하고 응답 저장) / `replay`(저장된 응답만, 없으면 실패) / `replay_or_live`
- 녹화본(cassette)은 객체 스토리지에 저장한다.
- 호출마다 토큰과 비용을 기록한다(RQ1·RQ4 지표의 원천).

### 10.2 이벤트 재생
- `change_event` 로그와 원문 스냅샷으로 과거 정정 흐름을 다시 흘려보낸다. 배속 조절 가능.
- 시간은 주입된 시계를 쓰고, 난수는 시드를 고정한다.

### 10.3 쓰임새
- **재현 가능한 실험**: `make eval` 하나로 녹화본 기준 실험표가 다시 나온다. LLM 비용 0.
- **서버 없는 데모**: 면접·발표 때 노트북에서 실제 정정공고가 들어오는 장면을 재현한다.
- **회귀 테스트**: 엔진 코드를 바꿀 때 과거 이벤트 결과가 달라지는지 CI에서 확인한다.

## 11. 보안과 격리

이전 보고서(LLM 에이전트 실행 환경의 격리·권한 설계)의 원칙을 이 시스템에 적용한다.

| 구성 요소 | 신뢰할 수 없는 입력 | 민감 정보 접근 | 외부 통신·상태 변경 | 설계 |
|---|---|---|---|---|
| 수집기 | 있음 (API 응답 속 첨부 URL) | 없음 | 있음 (다운로드) | https와 허용 호스트(기업마당)만, 리다이렉트마다 재확인, 크기·시간 상한 |
| 파서 컨테이너 | 있음 (외부 HWP/PDF) | 없음 | 없음 (네트워크 차단) | 표준 입력 바이트 → JSON 출력만. 시간 초과 시 컨테이너 종료, 출력 크기·모양 검사 |
| 추출 LLM | 있음 (공고 텍스트) | 없음 (프로필을 보지 않음) | 없음 (도구 없음) | 스키마 검증·인용 검증 통과한 값만 저장 |
| 판정기 | 없음 (검증된 규칙만) | 있음 (프로필) | 없음 | 결정적 코드 |
| 알림 워커 | **있음** (공고 제목·인용·추출 값) | 있음 | 있음 (발송) | 아웃박스에 기록된 것만, 타입 값과 이스케이프한 인용만, 링크 허용 목록, 붙잡기 정책(7.8) |

알림 워커는 세 능력을 모두 가진다. 그래서 신뢰할 수 없는 입력을 타입 값과 이스케이프한 인용으로 줄이는 정책 층을 발송 앞에 둔다. 나머지 구성 요소는 셋을 동시에 갖지 않는다(Rule of Two).
- 앱이 docker CLI를 직접 부르는 방식은 집 PC·단일 서버에서만 쓴다. 클러스터로 옮길 때는 docker 소켓을 주지 않고 무네트워크 파서 서비스로 바꾼다.

추가 원칙:
- 파서는 선택적으로 gVisor(runsc) 런타임에서 돌린다(범위가 넘치면 기본 컨테이너 격리로 대체).
- 프로필에는 주민번호 등 고유식별정보를 받지 않는다. 사업자등록번호는 선택 입력.
- 모든 화면과 알림에 "참고용, 최종 확인은 공고 원문" 문구와 원문 링크를 붙인다.

## 12. 평가 계획

### 12.1 데이터셋 (공개 산출물 후보)
- **구성**: 공고 원본·정정본 쌍, 버전별 조각, 필드 정답.
- **수집**: 2026-10-23부터 두 출처 열린 공고 전체를 6시간마다 스냅샷한다(7.1). 기업마당 API는 닫힌 공고를 주지 않아 과거 백필은 할 수 없다.
- **정답 라벨 (기준은 사람)**
  - 단위는 (이벤트, 필드). 필드별로 상태(바뀜 / 안 바뀜 / 문구만 바뀜 / 필드 없음), 정규화한 이전·이후 값, 정답 근거 위치, 어디서 보이는지(API 메타 / 본문 / 첨부)를 적는다.
  - **엔진을 돌리기 전에** 라벨한다. 화면은 엔진의 조각 비교가 아니라 파서와 무관한 원문 diff와 원본 첨부를 쓴다.
  - 7일 이상 지난 뒤 무작위 30%를 다시 라벨해 본인 일치도를 내고, 가능하면 두 번째 사람이 같은 30%를 라벨한다(Cohen's kappa).
  - "문구만 바뀜"과 정규화 규칙은 라벨링 전에 문서로 고정한다.
- **목표 규모**: 12/14까지 실제 정정 30~80건(그중 첨부에서만 보이는 변경 10~25건)으로 추정한다(가정). 목표는 **실제 40건 이상 + 합성 300건 + 음성 표본 200건**이며, 서로 섞지 않고 따로 보고한다. 합성 정정은 실제 HWPX의 텍스트를 고친 뒤 다시 파싱해 만들고, 연산자 집합은 엔진을 돌리기 전에 고정한다.
- **공개 조건**: 원문은 공개하지 않는다. 공고 ID·첨부 해시·라벨·생성 스크립트만 공개한다(기업마당 공공누리 3유형, K-Startup 약관).

### 12.2 비교 기준(베이스라인)
- **B0 메타 비교 (LLM 0회)**: API의 구조화 필드(접수 기간 등)만 코드로 비교한다. 마감 연장 같은 변경은 이것만으로 잡힌다. 엔진의 가치는 첨부·본문에서만 보이는 변경에 있다는 점을 정직하게 보여 준다.
- **B1 질문별 주기 재실행**: 실행하지 않고 비용은 계산식으로만 둔다. LLM 답 비교의 가짜 알림률을 재는 작은 부분집합에서만 돌린다.
- **B2 공고 단위 전체 재추출**: 변경된 공고의 필드를 전부 다시 추출한다. 엔진과 같은 변경 감지 관문, 같은 추출 프롬프트 버전을 쓴다.
- **B3 diff 기반 LLM**: 바뀐 조각(이전 → 새)과 이전 필드 값을 LLM에 주고 "무엇이 바뀌었고 새 값은 무엇인가"를 묻는다. 엔진이 B3을 이기지 못하면, 엔진의 기여는 "타입별 결정적 비교로 가짜 알림 억제 + 근거 위치 + 사용자 재판정을 코드로"로 정리한다.
- **제안 방식**: 변경 영향 엔진(7.7).

### 12.3 연구 질문별 측정

| RQ | 실험 | 지표 |
|---|---|---|
| RQ1 | B0·B2·B3·엔진을 같은 이벤트 로그로 재생, 결과를 "API 메타로 보이는 변경 / 첨부·본문에서만 보이는 변경"으로 나눠 보고 | 3장 RQ1 지표 |
| RQ2 | 조각 맞추기 변형을 합성 변형 세트와 실제 정정에 적용 | 놓친 변경, 잘못 잡은 변경, 처리 시간 |
| RQ6 | 2단계 파일럿 (ARCHITECTURE.md 8장) | 공격 성공률, 공격이 있을 때와 없을 때의 과제 성공률, 승인 요청 수 |

### 12.5 통계와 재현
- 비율에는 95% Wilson 구간을 붙이고, 같은 사업의 여러 정정은 사업 단위 군집 bootstrap으로 묶는다. 표본이 작아 비열등성 검정은 하지 않는다.
- **시간으로 개발·시험을 나눈다**: 11/20 이전 이벤트는 개발(임계값 등 조정)용, 이후는 시험용이고 시험 세트는 한 번만 돌린다. 주 지표는 시험 전에 정한다.
- 부분집합에서 같은 입력을 3번 추출해 LLM 분산을 보고한다. 평가에 쓰는 프롬프트 버전은 고정한다.
- 파서 비교 manifest(공고 ID, 첨부 sha256, 형식, 크기, 파서 버전, 결과)는 원문 없이 저장소에 커밋한다.

### 12.4 실사용 지표 (기간 한정 운영)
- 사용자 수, 주간 재방문, 받은 알림 중 "도움됨" 비율, 판정 오류 신고 건수.

## 13. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어·API | Python 3.12, FastAPI | 혼자 3개월에 가장 빠름. 파싱·LLM·임베딩 생태계가 Python |
| DB | PostgreSQL 16 + pgvector | 관계형 데이터와 벡터를 한 곳에서 |
| 큐 | PostgreSQL 작업 테이블 (SKIP LOCKED, lease) | DB 기록과 다음 작업 등록을 한 트랜잭션으로. 데이터 양이 작다 |
| 객체 스토리지 | SeaweedFS(로컬, S3 호환), Cloudflare R2(클라우드) | 내용 해시 키 저장, 무료 구간. MinIO는 커뮤니티 이미지 배포 중단으로 2026-10-19 교체 |
| 파서 | kordoc 4.18.13 (기본), hwp-hwpx-parser 1.0.0 (대체) | 실제 첨부 119개 비교 결과 (`docs/research/parsers.md`) |
| 임베딩 | 로컬 다국어 임베딩 모델 (CPU) | 비용 0 |
| LLM | 소형 API 모델 (기본 `claude-haiku-5-5`), 로컬 모델 비교 가능 | 바뀐 조각만 처리해 호출이 적음 |
| 웹 | FastAPI + Jinja2 + HTMX (서버 렌더링) | 프로세스 하나, 빌드 체인 없음. 화면은 읽기 전용 뷰로 DB를 읽는다 |
| 배포 | 1단계: 집 PC 예약 작업(수집) + VPS 1대의 docker compose(베타). 동결 뒤: k3s, KEDA, Terraform | 1단계는 끝낼 수 있는 크기로 |
| 관측 | OpenTelemetry, Prometheus, Grafana | 단계 간 추적과 지표 |
| 격리 | 컨테이너 제한 + (선택) gVisor | 신뢰할 수 없는 첨부 처리 |

나중에 Spring 경험을 넣고 싶으면 **알림 서비스만** 별도 Spring 서비스로 떼어 낸다. 아웃박스 → 큐 → 알림 서비스 경계가 이미 있어서 다른 부분은 바뀌지 않는다.
