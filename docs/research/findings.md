# 발표용 성과 기록

연구 질문(DESIGN 3장)과 그때그때 던진 질문에 대해 **숫자로 답한 것**만 모은다. 발표 자료는 여기서 꺼내 쓴다.
한 건의 모양: 질문 → 한 줄 답(슬라이드 제목감) → 숫자 → 어떻게 쟀나(다시 재는 명령) → 한계.
자세한 기록은 각 줄의 출처 문서에 있다.

## F1. 정정의 39%는 API 메타로 안 보인다 (RQ1의 배경)

- **질문**: 공식 API가 주는 구조화 값(접수 기간)만 비교해도 정정을 잡을 수 있나?
- **답**: 아니다. 조각이 실제로 바뀐 정정 49건(사업 48개) 가운데 30건만 API의 접수 기간이 바뀌었고, 19건(39%)은 본문·첨부에서만 바뀌었다.
- **어떻게**: `make eval`의 B0 줄과 입력 크기 표(LLM 없음). [eval.md](eval.md)
- **한계**: 30건 안에도 메타로 안 보이는 다른 변경이 함께 있을 수 있다(사람 라벨이 있어야 안다).

## F2. 첨부 파싱 94% (진행 판단의 근거)

- **질문**: HWP·HWPX·PDF가 섞인 공고 첨부를 기계가 읽을 수 있나?
- **답**: 첨부 119개 중 112개(94%). HWP·HWPX 70개는 전부, 실패 7개는 모두 글자 층이 없는 PDF(스캔본 6, 깨진 글꼴 1).
- **어떻게**: 파서 비교(kordoc 대 hwp-hwpx-parser). [parsers.md](parsers.md)

## F3. 개인정보 가리기와 인젝션 탐지 (하네스)

- **질문**: LLM에 보내기 전에 전화·이메일 등을 가렸다가 답에서 되돌리면 원문이 망가지지 않나? 실제 공고에서 인젝션 탐지가 오탐을 내나?
- **답**: 조각 847,174개 전수에서 되돌린 결과가 원문과 다른 조각 0개, 인젝션 의심 줄 0개.
- **어떻게**: `uv run python scripts/harness_scan.py`. [harness.md](harness.md)
- **한계**: 인젝션 탐지의 재현율은 직접 만든 공격 세트로만 쟀다(실제 공고에는 심은 지시가 없다고 본다).

## F4. 변경 영향 엔진은 전체 재추출보다 입력 토큰을 86% 덜 쓴다 (RQ1, 첫 실측)

- **질문**: 바뀐 조각과 영향받은 필드만 다시 묻는 엔진은 전체를 다시 뽑는 방식(B2)과 바뀐 조각만 LLM에게 판단시키는 방식(B3)에 비해 토큰을 얼마나 쓰나?
- **답**: 정정 30건에서 입력 토큰 B2 386,331 · B3 162,380 · **엔진 52,934**. 엔진은 B2의 13.7%, B3의 32.6%. 출력까지 더하면 B2 410,967 · B3 167,062 · 엔진 67,225(B2의 16.4%).

  | 방식 | LLM 호출 | 입력 토큰 | 출력 토큰 | "바뀌었다"고 본 정정 |
  |---|---|---|---|---|
  | B0 메타 비교 | 0 | 0 | 0 | 22 |
  | B2 전체 재추출 | 30 | 386,331 | 24,636 | 30 |
  | B3 바뀐 조각만 LLM에 | 30 | 162,380 | 4,682 | 27 |
  | **변경 영향 엔진** | 29 | **52,934** | 14,291 | 28 |

- **어떻게**: 부산대 피클 학교 모델 `pickle-general`(무료), 추출 틀 v1, 개발 세트. 녹화본으로 비용 없이 다시 낸다: `make eval`.
- **한계**: **정확도는 아직 모른다**(사람 라벨 0건). 엔진과 B2가 다르게 본 (정정, 필드) 32건이 라벨을 먼저 달 목록이다. 자격 규칙 "변경"은 B2 27 · 엔진 12 · B3 6인데, F8을 보면 상당수가 재추출 잡음이다.

## F5. 프롬프트 토큰의 절반 가까이는 조각 ID였다 → 짧은 번호로 26% 절감

- **질문**: 학교 모델 하루 한도 안에서 더 많이 재려면 어디를 줄여야 하나?
- **답**: 추출 프롬프트는 조각마다 `[833c25ad4b0b] 원문`처럼 12자리 ID를 붙인다. 녹화본 60개의 실제 입력 토큰을 프롬프트 부분별 글자 수로 회귀하면(중앙 오차 2.7%) **입력 토큰의 약 48%가 ID**였다. 조각의 66%가 표 칸이고 15%는 빈 칸이라, ID만 있고 내용이 없는 줄이 많았다.
- **고친 것**: 추출 틀 v2. 요청 안에서만 쓰는 짧은 번호(`[1] 원문`)를 붙이고 빈 조각은 뺀다. 답의 번호를 lineage_id로 되돌리므로 엔진·인용 검증·저장은 그대로다.
- **실측**: 같은 공고 9건에 v1과 v2. 입력 267,415 → 197,660(**−26%**), 출력 10,603 → 8,180(−23%). 값 일치율 66.7%로 잡음 바닥(F8, 71.1%)과 비슷하고, 마감·문의처는 차이가 없다.
- **겪은 것(발표 소재)**: 처음에는 근거 칸이 문자열이라 모델이 숫자를 따옴표 없이 쓰려다 형식에 막혀 공백만 끝없이 냈다. 정수 배열로 바꾸자 해결됐다. "형식을 지키게 하는 디코딩"이 오히려 모델을 가두는 사례다.
- **어떻게**: `uv run python scripts/template_ab.py --provider pickle --limit 30`. [eval.md](eval.md)
- **한계**: 9건, 모두 큰 공고. 예산 때문에 더 재지 못했다.

## F6. 무료 학교 모델은 받는 쪽을 고쳐서 쓴다

- **질문**: 유료 API 없이 학교 무료 모델로 연구 측정이 되나?
- **답**: 된다. 다만 모델의 출력 모양이 엉성하다. 근거 없는 필드를 빼라고 해도 `null`로 준다(20%), `value_json`에 JSON 대신 맨 글자를 넣는다, 자격 규칙의 `manual` 칸에 원문 문자열을 그대로 넣는다. 받는 쪽을 고쳐(타입별 모양 맞추기, 맨 글자 받기, 문자열 manual 받기) **자격 규칙 검사 통과 48% → 90%**.
- **어떻게**: 녹화본 90개 분석. [eval.md](eval.md)

## F7. 무료 모델의 하루 한도 = 평가 한 바퀴 → 미리 세고 예산을 건다

- **질문**: 하루 토큰 한도(약 100만)가 있는 무료 모델로 측정을 어떻게 끝까지 하나?
- **답**: 평가 한 바퀴(호출 90번)가 입력 99.7만 토큰으로 하루 한도를 다 써서 엔진 측정이 잘렸다. 그래서 (1) 보내기 전에 녹화본에 없는 호출만 골라 크기를 세는 "미리 세기", (2) 넘을 호출을 보내기 전에 막는 토큰 예산을 게이트웨이에 넣었다. 다음 날 엔진 측정은 미리 센 값(입력 12.9만)대로 실제 12.8만(입력+출력)을 쓰고 끝났다.
- **예산의 빈틈도 실제로 겪었다**: 출력 한도로 끝난 실패 응답은 예산에 안 잡혀서, 형식 고장(F5)이 난 호출들이 예산 밖에서 토큰을 썼다. 공급자가 센 토큰을 실패에도 실어 넣고, 출력 상한을 16,000 → 4,096으로 낮췄다.
- **어떻게**: `uv run python scripts/eval.py --provider pickle --plan`, `--budget N`. 같은 요청은 녹화본으로 다시 쓰므로 두 번 내지 않는다.
- **플랫폼으로서의 뜻**: 앱마다 LLM 예산을 두는 설계(app-spec 9장)의 첫 부품이다. 남의 앱을 돌리는 플랫폼이라면 "이번 실행이 얼마 드는지 먼저 보여 주기"가 기본이어야 한다.

## F8. 같은 글을 두 번 뽑아도 자격 규칙은 10건 중 9건이 다르게 나온다 (RQ1 잡음 바닥)

- **질문**: 같은 공고를 같은 틀로 두 번 뽑으면 값이 얼마나 달라지나? (RQ1 지표의 "B2 잡음 바닥")
- **답**: 값 일치율 71.1%(10건). 자격 규칙은 10건 중 9건이 다르게 나오고, 모양이 다른 7쌍 중 6쌍은 가상 프로필 500명에게 판정까지 달랐다. 제출 서류 3건. **마감·금액·문의처는 모두 같았다.**
- **뜻**: B2가 "자격 규칙이 바뀌었다"고 한 27건은 대부분 잡음일 가능성이 크다. 엔진은 규칙에 걸린 조각이 바뀔 때만 다시 물어 12건이다. 잡음에 덜 노출되는 것도 엔진의 이득이다.
- **해 본 것**: 근거 검사("값이 달라져도 근거 조각이 그대로면 변경이 아니다")는 효과가 작았다(엔진의 규칙 12 → 11). 다음 후보는 조건 하나하나의 근거를 보거나, 규칙을 속성마다 칸이 정해진 평평한 모양으로 뽑는 것.
- **어떻게**: `uv run python scripts/template_ab.py --provider pickle --limit 15 --noise`. [eval.md](eval.md)
- **한계**: 10건. 예산으로 15건 중 5건은 못 쟀다.

## F9. 온도 0도 같은 답을 보장하지 않는다

- **질문**: 온도를 0으로 두면 같은 요청에 같은 답이 오나?
- **답**: 아니다. 가장 작은 공고 하나를 같은 요청으로 두 번 보내자 첫 자격 규칙의 속성부터 갈렸다(출력 447 대 501토큰).
- **뜻**: 설계 초기에 정한 녹화·재생(DESIGN 10장)이 재현의 유일한 길이다. 모든 측정표는 녹화본으로 비용 없이 같게 다시 나온다(`make eval`).

## F10. 출처 단위의 판 하나를 앱마다 자기가 읽는 키로 거른다 (플랫폼 3번)

- **질문**: 한 출처를 여러 앱이 읽을 때, 앱이 읽지 않는 키만 바뀐 판도 변경으로 흘려야 하나?
- **답**: 아니다. 변경을 기록할 때 원본에서 바뀐 키를 남기고, 앱은 자기가 읽는 키와 겹칠 때만 변경으로 받는다. 아니면 영향 계산이 LLM을 부르지 않고 앞 판의 값을 그대로 넘긴다.
- **실제 데이터**: 첫 판을 뺀 변경 60건 중 9건이 이 앱에게 변경이 아니다. 앱이 읽지 않는 키만 바뀐 4건(기업마당 `hashtags` 3, `printFileNm` 1), 조각이 하나도 안 바뀐 5건(제목만, 표기만).
- **어떻게**: `uv run python scripts/change_keys.py`. [app-spec.md](../app-spec.md) 12장
- **한계**: 앱이 하나뿐이라 지금 이득은 작다. 두 번째 앱이 같은 출처의 다른 키를 읽을 때 조각 단위까지 내려가야 한다.

## F11. 첫 정확도: 엔진은 B2만큼 찾고 가짜 알림은 덜 낸다. 다만 제출 서류가 약하다 (RQ1, AI 라벨)

- **질문**: 방식마다 진짜 변경을 얼마나 찾고, 가짜 알림을 얼마나 내나?
- **라벨**: 개발 세트 30건 × 필드 5개 = 150개. Claude가 달았다(`labeler=claude`).
  - 엔진의 조각 비교는 보지 않았다. 원문 글자 비교(API 값, 본문+첨부 낱말 비교)만 보고 지침 v1대로 달았다.
  - Claude가 애매하다고 표시한 칸은 사람이 판정했다(5칸, `labeler=me`). 채점은 AI 라벨을 사람 판정으로 덮어쓴 것으로 한다.
    - 12번: 제목만 [마감]으로 바뀐 것을 조기 마감, 즉 "바뀜"으로 봤다.
    - 05·06번 금액: "알릴 변경 아님"으로 봤다.
    - 27번: 마감과 서류 모두 "바뀜"으로 봤다.
  - 실제로 바뀐 것은 36개다. 마감 24, 자격 6, 서류 4, 문의처 2, 금액 0.
- **답** (재현율 / 정밀도 / 가짜 알림률):

  | 방식 | 재현율 | 정밀도 | 가짜 알림률 | 입력 토큰 |
  |---|---|---|---|---|
  | B0 메타 비교 | 0.61 | 1.00 | 0% | 0 |
  | B2 전체 재추출 | 0.92 | 0.48 | 32% | 386,331 |
  | B3 diff 기반 LLM | 0.78 | 0.78 | 7% | 162,380 |
  | 변경 영향 엔진 | 0.83 | 0.53 | 24% | 52,934 |

- **필드별로 본 것**:
  - 자격 규칙: 실제로 바뀐 것은 6건이다. B2는 가짜 알림 22건으로 잡음 바닥(F8)이 그대로 드러났다. 엔진은 8건, B3는 2건이었다.
  - 제출 서류: 엔진의 가짜 알림이 11건으로 B2(8건)보다 많다. 엔진에서 가장 먼저 고칠 곳이다.
  - B3: 가짜 알림은 가장 적지만, 제출 서류 변경 4건을 모두 놓쳤다. 본문·첨부에서만 보이는 변경도 8건 중 4건만 찾았다(엔진·B2는 7건).
  - 마감: 모든 방식이 24건 중 22건을 찾았다. B0도 22건이다. 마감은 API 메타만으로 대부분 잡힌다.

## F12. 같은 입력을 다시 흘려 같은 출력이 나오는지 잰다: 22개 실행이 모두 같았고, 재생이 버그 둘을 잡았다 (플랫폼 4번)

## F13. 엔진의 서류 가짜 알림 11건 → 1건, 토큰 0으로 (RQ1)

- **질문**: F11에서 엔진의 약점이던 제출 서류 가짜 알림 11건은 왜 생겼나?
- **원인** (녹화본으로 엔진이 들고 다닌 값을 꺼내 봄):
  1. **표기 차이**(절반 정도): 서류 이름은 같은데 글자가 달랐다.
     - 수량("1부"), 서식 머리표("[별지 1]"), 띄어쓰기("장관표창에대한"), 괄호 설명이 달랐다.
     - HWP 기호 글꼴의 공백(U+F0A0)이 섞인 경우도 있었다.
     - 목록 비교가 글자 그대로였다.
  2. **일부만 다시 뽑은 목록**(나머지): 엔진은 바뀐 조각과 그 필드의 옛 근거만 다시 읽는다. 그래서 서류 목록의 일부(5개, 1개)만 돌아와 전체 목록을 덮어썼다. 실제로는 서류가 빠지지 않았다.
- **고친 것**:
  - 공통 비교(모든 방식): 서류 이름의 열쇠로 비교한다. 수량, 머리표, 괄호, 띄어쓰기·문장부호를 빼고, 한쪽이 다른 쪽에 들어 있으면 같은 서류로 본다.
  - 엔진: 목록이 달라졌다고 나오면 원문으로 한 번 더 본다.
    - 빠졌다는 서류가 새 판 글에 아직 있으면 빠진 것이 아니다.
    - 생겼다는 서류가 옛 판 글에 이미 있었으면 새로 생긴 것이 아니다.
- **결과** (개발 세트, AI 라벨 + 사람 판정, 녹화본 재생이라 **LLM 토큰 0**):
  - 엔진의 서류 가짜 알림: 11 → **1**. 남은 1건(26번)은 새 공고문 PDF의 글자가 깨져 원문으로 확인할 수 없다.
  - 진짜 서류 변경을 맞힌 수는 2건으로 그대로다.
  - B2의 서류 가짜 알림: 8 → 4(공통 비교의 효과).
  - 엔진 전체: 정밀도 0.53 → **0.64**, 가짜 알림률 24% → **15%**. 재현율은 0.83 그대로다.
- **뜻**: 부분 재추출은 토큰을 아끼지만 목록처럼 "전체를 봐야 하는" 필드에는 맹점이 있다. 그 맹점은 LLM을 더 부르지 않고, 원문을 글자로 확인하는 것만으로 메웠다.
- **한계**: 개발 세트를 보며 고쳤다. 시험 세트로 다시 재야 한다. 엔진이 놓친 서류 변경 2건(07, 14)은 아직 그대로다.

## F14. 마감은 출처 값으로, 나머지는 엔진으로: 지금까지 가장 좋은 조합 (RQ1)

- **질문**: 앱 정의에서 마감은 "출처가 구조화해 준 값(meta)에서 읽는 필드"다. 그런데 엔진은 마감도 LLM에 다시 묻는다. 마감을 출처 값으로 판단하면 어떤가?
- **먼저 고친 것**: 제목에 [마감]이 붙으면 기간 값이 그대로여도 마감을 "마감"으로 읽는다(`programs.closed_by_title`). F11에서 모든 방식이 놓친 12번(조기 마감)이 이제 잡힌다.
- **답** (개발 세트, AI 라벨 + 사람 판정, 녹화본 재생, LLM 토큰 0):

  | 방식 | 재현율 | 정밀도 | 가짜 알림률 |
  |---|---|---|---|
  | B0 메타 비교 (LLM 없음) | 0.64 | 1.00 | 0% |
  | 변경 영향 엔진 | 0.83 | 0.64 | 15% |
  | **엔진 + 출처 값(마감)** | **0.86** | **0.66** | **14%** |
  | B2 전체 재추출 | 0.92 | 0.51 | 28% |

  - 마감: 출처 값으로 24건 중 23건을 찾고 가짜 알림은 0이다. LLM으로는 22건을 찾고 가짜 알림이 1건이었다.
- **토큰**:
  - 엔진의 LLM 호출 29개 중 9개(31%)가 마감만 다시 묻는 호출이다. 이 조합에서는 부르지 않아도 된다.
  - 다만 작은 호출이라 토큰으로는 4,269개(엔진의 6%)다. 호출 수(속도, 한도)가 크게 줄고 토큰은 조금 준다.
- **뜻**: 출처가 구조화해 주는 값은 LLM보다 정확하고 공짜다. 엔진은 출처가 주지 않는 것(자격, 서류, 문의처)에만 LLM을 쓰면 된다. 운영 파이프라인은 아직 앱 정의의 `from: meta` 필드를 출처 값으로 읽지 않는다. 추출기를 붙일 때 함께 해야 한다.
- **한계**: 개발 세트 30건이다. B2와 비교하면 재현율이 0.06 낮다. 놓치는 것은 주로 엔진이 다시 묻지 않은 자격(2건)·서류(2건) 변경이다.
