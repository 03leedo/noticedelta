# 평가 골격과 LLM 없이 잰 것 (2026-11-16)

RQ1(DESIGN 3장)을 재는 틀. 코드는 `src/noticedelta/evaluation/`, 실행은 `make eval`.

## 틀

기록된 정정 이벤트를 방식별로 다시 돌려 같은 표에 놓는다.

| 방식 | 하는 일 | LLM |
|---|---|---|
| B0 메타 비교 | API의 구조화 필드(접수 기간)만 코드로 비교 | 0회 |
| B2 전체 재추출 | 새 버전 전체를 다시 추출해 이전 값과 타입별 비교 | 이벤트마다 1회, 전체 조각 |
| B3 diff 기반 LLM | 바뀐 조각(이전 → 이후)과 이전 값을 주고 무엇이 바뀌었는지 묻는다. 답을 그대로 믿는다 | 이벤트마다 1회, 바뀐 조각 쌍 |
| 변경 영향 엔진 | 영향받은 필드만, 바뀐 조각과 기존 근거만 다시 추출해 타입별 비교 | 영향이 있을 때만 |

- 정답은 사람 라벨뿐이다(`label` 테이블). 단위는 (이벤트, 필드). 재현율·정밀도·가짜 알림률을 95% 구간(Wilson)과 함께 내고, 재현율은 "API 메타로 보이는 변경"과 "본문·첨부에서만 보이는 변경"으로 나눠 본다.
- 사업 ID로 개발·시험 세트를 가른다. 프롬프트와 규칙은 개발 세트만 보고 고치고, 시험 세트의 정확도는 측정 동결 때만 본다.
- LLM은 녹화본으로만 돈다(비용 0). 녹화본이 없는 방식은 "판단함 0"으로 나오고 지표에서 빠진다.
- 방식은 추출기와 게이트웨이를 밖에서 받는다. 하네스를 켠 게이트웨이를 주면 표에 한 줄이 더 생긴다(`--harness personal`). 하네스 실험의 바탕이다.
- 안전망(DESIGN 7.7)의 불일치 목록: `scripts/eval.py --disagreements`가 엔진과 B2가 다르게 본 (이벤트, 필드)를 낸다. 정답이 아니라 사람이 볼 목록이다. 운영 중 그림자 실행과 주간 10% 표본은 LLM이 연결된 뒤에 붙인다.

## 지금 잴 수 있는 것 (LLM 호출 없음, 라벨 없음)

대상: 조각이 실제로 바뀐 정정 49건(사업 48개). 개발 세트 22건, 시험 세트 27건.

**입력 크기**: 이벤트마다 LLM에 넘길 조각 글자 수.

| 방식 | 합계 | 이벤트 중앙값 | B2 대비 합계 | B2 대비 중앙값(이벤트별 비율) |
|---|---|---|---|---|
| B2 전체 재추출 | 661,686 | 7,148 | 100.0% | 100.0% |
| B3 바뀐 조각 쌍 | 323,924 | 1,179 | 49.0% | 24.5% |
| 엔진 (하한: 바뀐 조각만) | 175,021 | 486 | 26.5% | 9.4% |

- 엔진 값은 **하한**이다. 실제로는 영향받은 필드의 기존 근거 조각이 더 붙는다. 추출 결과가 있어야 정확한 값이 나온다.
- 합계 비율(26.5%)이 중앙값(9.4%)보다 큰 것은 첨부가 통째로 바뀐 큰 정정 몇 건이 합계를 끌어올리기 때문이다. 대부분의 정정은 작다.
- 글자 수이지 토큰 수가 아니다. 프롬프트의 고정 부분(지시문, 스키마)은 넣지 않았다.

**B0가 보는 것**: 49건 중 30건에서 API의 접수 기간이 바뀌었다. 나머지 19건(39%)은 API 메타에 변화가 없고 본문·첨부에서만 바뀌었다. 30건 안에도 메타로 안 보이는 다른 변경이 함께 있을 수 있다(라벨이 있어야 안다).

## 피클 학교 모델로 처음 돌린 것 (2026-11-24)

LLM 키(부산대 피클 게이트웨이, `pickle-general`: vLLM으로 돌리는 Qwen 계열, 무료)가 생겨 처음으로 실제 추출을 돌렸다. 사람 라벨이 아직 없어 정확도는 재지 못하고, 각 방식이 "바뀌었다"고 본 수와 비용만 나온다.

```
uv run python scripts/eval.py --provider pickle --mode replay_or_live --disagreements
```

대상: 개발 세트 정정 30건(사업 30개, 이 날의 DB 기준).

| 방식 | 판단함 | 변경 있다고 봄 | LLM 호출 | 입력 글자 |
|---|---|---|---|---|
| B0 메타 비교 | 30 | 22 | 0 | 0 |
| B2 전체 재추출 | 30 | 29 | 30 | 338,645 |

| 변경 영향 엔진 | 1 | 0 | 0 | 0 |

- 처음 추출(사업마다 1번) 30번, B2 재추출 30번, B3 30번, 합계 90번. 입력 996,796토큰, 출력 54,227토큰. 비용 0.
- **엔진 줄은 측정이 아니다.** 엔진이 마지막에 돌 때 키의 하루 토큰 한도(약 100만)에 걸려 `429 quota_exhausted`로 모두 거절됐다. B2·B3의 녹화본은 남아 있으므로, 한도가 풀린 뒤 같은 명령을 다시 돌리면 엔진 호출만 새로 나간다.
- B2는 30건 중 29건을 "바뀌었다"고 봤다. B0(메타)가 22건이므로 7건은 본문·첨부에서만 보였거나, 전체를 다시 뽑으면서 값이 흔들린 것이다(같은 글을 다시 뽑아도 표현이 달라지는 경우). 어느 쪽인지는 라벨이 있어야 가른다. 이것이 B2의 가짜 알림 위험이다.
- 엔진과 B2가 다르게 본 (이벤트, 필드)는 지금 1건(엔진이 판단한 1건 안에서)이다.

**겪은 것**

| 문제 | 원인 | 고친 것 |
|---|---|---|
| 평가가 10번째 호출에서 죽음 | 학교 모델이 없는 필드를 빼지 않고 `null`로 줬고, 목록 비교가 `None`을 돌다 터졌다 | LLM 값을 타입에 맞는 모양으로 맞추고 못 맞추면 "값 없음"으로(`values.coerce_shape`) |
| 55번째 호출에서 죽음 | 모델 서버가 붐벼 `504 upstream_timeout` | 504도 다시 보내고, 끝내 실패한 호출은 그 사업만 "호출 실패"로 빼고 계속 |
| 엔진 호출이 모두 거절, 실행이 오래 걸림 | 하루 토큰 한도. 429라서 매번 기다렸다 다시 보냈다 | 한도 거절(`quota_exhausted`, `credit_*`)은 다시 보내지 않는다 |
| curl 시험이 400 | Windows Git Bash에서 명령줄의 한국어가 깨졌다 | 본문을 UTF-8 파일로 보낸다(코드의 호출에는 해당 없음) |

**같은 날 이어서: 학교 모델의 출력 모양** (녹화본 90개 분석)

- 추출 60번에서 필드 300개가 왔다. 요청한 다섯 필드를 늘 모두 준다(근거가 없으면 빼라고 했는데 `null`로 준다): `null` 60개(20%), `value_json`이 JSON이 아닌 것 12개(4%), 모양이 틀린 것 2개.
- **자격 규칙은 60개 중 29개(48%)만 검사를 통과했다.** 실패 대부분(121건)은 `manual`(속성 사전으로 못 바꾼 조건) 칸에 `{"text": …}` 대신 원문 문자열을 그대로 넣은 것이었다. 문자열이면 그 글을 받도록 고치자 54개(90%)가 통과한다. 남은 실패는 `in`에 목록이 아닌 값, `"true"` 같은 문자열 불, "5000달러 이상" 같은 금액.
- 이 수정으로 B2는 30건 모두 "바뀌었다"고 보게 됐고(B0는 22건), B3는 "정정 전 값"이 달라져 15건의 녹화본이 맞지 않게 됐다. 한도가 풀리면 다시 받는다.
- 입력 중앙값 8,414토큰, 출력 중앙값 783토큰.

## 잡음 바닥: 같은 글을 두 번 뽑으면 (2026-11-25)

같은 공고의 첫 판을 같은 틀(v1)로 한 번 더 불렀다. 두 번째 녹화본은 `data/cassettes-repeat`에 따로 둔다(키가 같아서).

```
uv run python scripts/template_ab.py --provider pickle --limit 15 --noise --budget 150000
```

| 비교 | 문서 | 값 같음 | 다름 | 한쪽에만 | 둘 다 없음 | 일치율 |
|---|---|---|---|---|---|---|
| v1 대 v1 다시 | 10 (예산으로 5 못 함) | 27 | 10 | 1 | 12 | 71.1% |

- **자격 규칙은 10건 중 9건이 다르게 나왔다**(8건 다름, 1건 한쪽에만). 제출 서류 3건. 마감·금액·문의처는 있는 것은 모두 같았다.
- 모양이 다른 규칙 7쌍을 가상 프로필 500명에게 판정해 보면 6쌍은 판정까지 달랐다. 표현만 흔들리는 것이 아니라 뽑힌 조건 자체가 다르다.
- **온도 0이어도 같은 답이 나오지 않는다.** 가장 작은 공고 하나를 같은 요청으로 두 번 보내자 첫 규칙의 속성부터 갈렸다(447 대 501 출력 토큰). 녹화·재생(DESIGN 10장)이 재현의 유일한 길이다.
- 엔진이 B2보다 자격 규칙 "변경"이 적은 것(12 대 27)은 규칙에 걸린 조각이 바뀔 때만 다시 묻기 때문이다. 잡음에 덜 노출되는 것이 엔진의 또 다른 이득이다.

**시도했지만 효과가 작았던 것: 근거 검사.** "새 값이 바뀐 조각을 근거로 들거나 옛 값의 근거가 바뀌었을 때만 변경"으로 거르면 엔진의 자격 규칙 12 → 11, 제출 서류 13 → 12, 금액 3 → 2(녹화본으로 잼, 토큰 0). 엔진은 다시 물을 때 바뀐 조각을 함께 주므로 모델이 규칙 차이와 상관없이 그 조각을 근거로 든다. 코드에는 넣지 않았다. 규칙 하나하나(조건 단위)로 근거를 보거나, 규칙을 속성마다 칸이 정해진 평평한 모양으로 뽑는 쪽이 다음 후보다.

## 토큰 아끼기: 추출 틀 v2 (2026-11-25)

녹화본 60개의 실제 입력 토큰을 프롬프트 부분별 글자 수로 회귀하면(중앙 오차 2.7%) 입력 토큰의 약 48%가 조각 ID(`[833c25ad4b0b]`)였다. 조각의 66%가 표 칸이고 15%는 빈 칸이다. v2는 요청 안에서만 쓰는 짧은 번호(`[1]`)를 붙이고 빈 조각을 빼며, 답의 번호를 lineage_id로 되돌린다.

```
uv run python scripts/template_ab.py --provider pickle --limit 30 --budget 170000
```

| 비교 | 문서 | 입력 토큰 v1 → v2 | 출력 토큰 v1 → v2 | 값 일치율 |

- 값 일치율 66.7%는 같은 틀을 두 번 돌린 잡음 바닥(71.1%)과 비슷하다. 다른 칸은 자격 규칙·제출 서류(원래 흔들리는 필드)와 v2만 찾은 금액 1건이다. 마감·문의처는 차이가 없다.
- 표본이 9건이고 큰 공고(한 건에 입력 약 3만 토큰)부터라 더 재야 한다. 개발 세트의 녹화본은 v1이므로 평가 표는 v1로 둔다(`--template extract-v1`이 기본). 시험 세트를 처음 받을 때 v2로 받으면 그만큼 싸다.

**v2를 만들며 겪은 것**

| 문제 | 원인 | 고친 것 |
|---|---|---|
